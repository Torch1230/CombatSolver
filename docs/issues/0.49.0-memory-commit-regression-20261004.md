# 0.49.0 内存提交回归

2026-10-04 固定日志站 18 份 0.49.0 未处理报告，涉及 16 个战斗 session，四个角色。逐包身份与报告信号见 [结构化分类](0.49.0-memory-commit-regression-20261004.json)。这些包的计算失败首因均为 `InvalidOperationException：不可分割的搜索提交在 NoGC 回退后仍受分配上限约束。`；包内重复日志不作为独立机制。

## 首因与版本来源

代表包 `3a5376fa0a63464fa43619b3fbf81404` 是储君对残杀千足虫。异常前的系统内存使用为 14,390,943,744 字节，策略内存线为 14,354,504,085 字节；分配窗为 268,435,456 字节，单父节点预约为 100,663,296 字节，但系统可用预约余量为 0。搜索进入显式普通 GC 回退，完成真实后台回收后又配置同一类有限分配窗，随后触发搜索提交的契约断言。

普通 GC 分配限制来自合入 0.49.0 的 `0b5b18e4f`。该变更让常规检查点与显式不可分割退出共用 `keepDefaultGcLimit: true`；搜索的显式退出合同则要求运行时接管分配。两条路径的语义被合并，是本轮共同回归首因。异常链完全位于 CombatSolver 的内存管理和搜索提交路径，原版遭遇均能触发；修复在仅链接生产 Runtime 代码的独立 .NET 9 进程中复现和验证。

## 修复与验证

Runtime 的常规检查点继续刷新请求分配上限；显式不可分割提交回收后使用 CLR 普通分配与回收。Search 原有契约断言保留。退出后下一请求重新建立自己的上限，取消在执行检查点前传播，已有 NoGC 恢复资格与退出约束保持。

- 未改生产代码的 `default-commit` Failed，失败点为显式退出后分配上限仍有效。
- 修改后的 `default-commit` 2 项 Passed，验证真实回收、提交可续行、下一请求上限与取消边界。
- `default-entry` 2 项、`recovery-lifecycle` 3 项 Passed，覆盖相邻诊断清理与真实 CLR 区域退出/恢复。

这些合同证明共同内存回退机制，不代表已复跑原包整场战斗、可见 Steam 或低内存玩家宿主性能。报告 `45f9d8754ac64df6a344dd967c9688ba` 同时含一次搜索结果过期信号；该信号的独立原因未作为本轮修复结论。

修复定稿为 0.49.1 紧急修复。日志站接口当前仅授予读取权限，服务器报告保持原状态。
