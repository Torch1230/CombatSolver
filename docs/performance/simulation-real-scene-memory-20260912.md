# 合并上游后的真实机甲场景内存与耗时对照

**测量日期：2026-09-12**  
**源码基线：`d419a80` + 本轮修复的单一性能预设断言；上游 `main` 已合入 `eff8cf4`（0.36.4）。**

## 结论

在同一个真实 Linux headless 游戏请求中，用相同的 30 张牌、种子、敌人、搜索预算和 DOP8 先后测量旧模型后端与现有紧凑后端，三次独立进程样本都保持完整逻辑结果一致：

- **搜索耗时中位数：11.602 秒 → 5.272 秒，减少 53.9%，约 2.20 倍。**
- **累计分配中位数：5.074 GB → 2.559 GB，减少 49.6%。**
- **进程 CPU 时间中位数：37.185 秒 → 17.639 秒，减少 52.0%。**
- **结束时工作集：1.803 GB → 1.674 GB，减少 7.15%。** 这是结束时读数，不是峰值 RSS。
- **Gen0/1/2 总回收次数：932 → 408，减少 56.2%。**

这组结果证明，**现有 Compact 后端在这个已准入的真实机甲场景确实把计算和分配大幅压低**。它不能直接外推到未准入的亡灵、药水、复杂遗物，也不能写成所有 Runtime/Steam 场景都能稳定 2 倍。

## 测量形状

入口是 `COMPACT-SEARCH-BACKEND`，它在同一个请求中使用同一个捕获根和搜索政策依次测量旧模型后端与 Compact 后端，再逐字段比较完整路线。固定输入如下：

| 项目 | 值 |
|---|---|
| 角色 / 种子 / 敌人 | `SILENT` / `VH_PERF_MECHA` / `MECHA_KNIGHT_ELITE` |
| 牌组 | `coverage/unattended/compact-void-admission-silent-run-cards.json`，30 张 |
| 预算 | `VeryHigh`，单一 Profile，Beam 135，节点 100,000，分支 72 |
| 并行度 | DOP8 |
| 模式 | Linux headless，`Instant`，每次独立进程，`--exit-on-complete` |
| 搜索工作量 | 14,344 节点、120,179 转移、69,527 选牌分支 |
| 结果 | `equivalent=true`，100,571 次完成回放、19,609 次挂起回放、0 次兼容物化 |

`VeryHigh` 断言本身也由真实请求驱动并通过，输出已从旧的 Short/Deep 双值格式改为上游 0.36.4 当前的单一 Profile 格式。

## 三次样本的原始中位数

| 指标 | 模型后端 | Compact 后端 | Compact 相对减少 |
|---|---:|---:|---:|
| 搜索耗时 | 11,602 ms | 5,272 ms | **53.9%** |
| 累计分配 | 5,073,540,064 B | 2,558,616,936 B | **49.6%** |
| 进程 CPU 时间 | 37,185 ms | 17,639 ms | **52.0%** |
| 结束时 managed heap | 350,656,808 B | 182,318,544 B | 48.0% |
| 结束时工作集 | 1,803,206,656 B | 1,674,252,288 B | **7.15%** |
| Gen0/1/2 总次数 | 932 | 408 | **56.2%** |

工作量、路线、终局回合和预计战损在三次样本中均逐项相同。三次样本的耗时减少范围为 53.7%–54.9%，累计分配减少范围为 49.5%–49.6%；结束工作集减少范围为 6.1%–10.1%。

完整逐样本数据见 [`simulation-real-scene-memory-20260912.json`](simulation-real-scene-memory-20260912.json)。原始 headless `result.json`、`compact-search-backend.json` 和日志保存在本轮私有证据目录中。

## 额外内存切口的结论

本轮把最新数据布局研究中最容易接入的一项做成真实代码候选：为 `PredictionStateStore` 的 `ReadEntries<TState>()` 增加结构枚举器和可复用缓冲区，并把三个热调用点改为新入口。独立合同检查通过：

- 新的结构枚举路径 500 次调用分配 **0 B**；
- 原 `ReadEntries().ToArray()` 形状同样 500 次分配 **108,000 B**；
- 既有读取、Fork、alias、重映射、顺序和边界检查全部通过。

但把该候选放进上述真实场景后，收益没有达到进入生产的标准：

- 模型后端累计分配中位数只变化 **0.22%**，小于本次整场测量的漂移；
- Compact 后端累计分配变化约 **0%**；
- 两个后端的结束工作集都没有下降，反而在独立进程噪声范围内略高；
- 因此本轮已撤回该候选的生产改动，只保留本报告和原始研究证据。

这说明“某个局部 API 可以做到零分配”不等于“真实搜索内存会明显下降”。当前不建议为了这笔小收益继续扩大 `PredictionStateStore` 的改造。

## 还能怎么压缩内存

按当前证据，优先级应是：

1. **先保留现有 Compact 后端的收益。** 对已准入的机甲样例，累计分配约少一半；这是目前最确定的内存收益，但覆盖范围有限。
2. **重新测量 NoGC / GC 策略，而不是继续迁移战斗语义。** 更小的 NoGC 预算可以直接限制区域内累计分配形成的驻留上限，但可能增加回收和耗时。应使用同一根、16/8/4 GB 交错 A/B，记录峰值 RSS、工作集、GC 暂停、路线和总耗时。
3. **审计 Power 模型克隆。** 历史剖析中 `ForkPower` 和 `DynamicVarSet.Clone` 是 Fork 分配与 CPU 的大项；空 `DynamicVarSet` 快路径可能是低于完整 Power 状态迁移的切口，但必须先证明空值比例和 Hook/身份合同。
4. **审计监听缓存数组重映射。** `RemapCachedModels`、`RemapCachedPowers` 每个保留节点复制派生数组，同时影响分配和驻留；应先计量每次 Fork 的数组长度、复制字节和保留节点数，再决定是否复用或分层存储。
5. **控制 Beam / wave 保留宽度。** `OwnedExpansionBatch`、父节点预约和固定 lane 缓冲更直接影响峰值驻留，但会改变搜索并行度，需要固定工作量的质量差分。
6. **暂不做整套状态族迁移或全量 Compact 闭包。** 目前没有证据表明它能以低维护成本进一步稳定降低全场景峰值；亡灵、药水、遗物和 AEONGLASS 仍是独立语义边界。

## 限制

- `baselineResources` 和 `candidateResources` 是 headless coordinator 搜索期间的进程级增量，包含游戏和原生后台工作。
- `workingSetAtEndBytes` 是每个后端测量结束时的工作集，不是 `/proc` 的峰值 `VmHWM`，所以不能把 7.15% 写成峰值 RSS 降幅。
- 这次 A/B 直接调用 coordinator，没有进入 Runtime NoGC 生命周期，也不是可见 Steam 的最终验收。
- 原始亡灵完整输入没有 Compact 对照，不能把机甲样例的数字外推到所有牌组。
- `codex://threads/01a08b0c-8d22-7023-b524-4e21e96bf95c` 仍无法通过当前工具读取；本报告只使用仓库中可访问的旧性能文档和当前源码，不声称读过该线程。
