# 当前安装版本的生命回复来源审计：第一阶段

本记录接续 C58/C59 生成闭包研究。研究分支已快进合入上游 `a789aad2`（0.48.0）；上游同时包含 PR #199、#200 与通用已知回复策略。本阶段提供原生入口清单和已复核的机制，不新增运行时剪枝，也不宣称所有原版模型已获得封闭认证。

## 版本与证据

- 游戏 `v0.111.0`，提交 `41cef1ea`，安装目录 `data_sts2_linuxbsd_x86_64/sts2.dll`。
- DLL SHA-256：`2b40d2df538db1ceb5fa48d958c80ab730ada1e07db88a870aff01a661768b9f`；MVID：`8a76776c-0ce1-4d4f-90bd-8cce653dad8e`。
- 工具 [HealingSourceAudit](../../tools/inspection/HealingSourceAudit/README.md) 读取 IL 元数据，不执行游戏代码。扫描 9,760 个含嵌套类型、51,602 个方法，其中 50,816 个有方法体；保存 339,688 条静态方法/委托引用和 2,657 条异步方法映射。
- 11 个生命命令/内部入口有 103 条直接引用、75 个来源类型；两项生命私有字段有 8 条写入，全部位于 `Creature`，没有取址指令。另保存 312 个选定回复回调定义、8,340 个模型虚方法和301条 Hook 调用引用。后两项覆盖金币、永久牌组、召唤及侧回合等间接入口，数量是调查覆盖率，不能当作语义认证率。
- 原始 IL 清单、114 次原生类型提取和提取文件哈希保存在忽略目录 `.local/general-healing-audit/`；提交的 JSON 保留直接入口引用及提取来源元数据，不提交游戏源码。
- 既有 [C58 语义审计](regent-potion-cap-bound-semantic-audit-20261003.json) 使用相同 DLL 哈希，其八个规范池、545 张可生成卡、178 种 Power 的结论仅在原来单人、原生池、解锁与扩展限制成立时复用。它不是全部原版内容或所有回调的认证。

## 状态的含义

下表“已复核”表示所述原生目标、时点及行为有当前 DLL 的直接证据。实际剪枝仍须认证全部可达来源、回调、所有牌堆和分支状态。表中“零”也只表示该具体命令不会增加玩家生命；目标错误、额外回调或间接来源未知时不能使用零上界。未获得完整证明的机制继续保留完整回复余量。

上游 `KnownSources` 使用原版程序集资格和已知回复来源，是独立的策略估计：忽略未来随机药水治疗。该估计不能被写成封闭语义证明。严格认证不能因为模型来自原版程序集，或没有直接 `Heal` 引用，就默认安全。

## 生命值入口与回调链

| 入口 | 当前原生行为 | 对上界的要求 |
| --- | --- | --- |
| `CreatureCmd.Heal` | `Creature.HealInternal` 增加当前生命并钳制于上限；死亡到存活会恢复玩家监听及触发 `Revived`；之后调用 `AfterCurrentHpChanged` | 回调收到的是请求量，不能仅用实际生命差反推回调效果 |
| `GainMaxHp` | `SetMaxHp` 后，按实际上限增量调用 `Heal` | 增加上限同时可能回复生命，不能排除在治疗入口外 |
| `SetMaxAndCurrentHp` | 先写上限，再写当前生命 | 须证明目标及调用时点；不能按治疗文案判断 |
| `SetCurrentHp` / 内部 setter | 可增可减，也用于初始化、读档与同步 | 玩家重设生命值未知时保留完整余量 |
| `SetMaxHpInternal` / `LoseMaxHp` | 前者单独不会提升当前生命；降低上限可能压低当前生命 | 命令本身不是玩家回复，后续死亡与扩展回调仍需审核 |
| 死亡命令 | `BeforeDeath`、`ShouldDie`/`ShouldDieLate`、`AfterDeath`、`AfterPreventingDeath`；阻止死亡路径还会处理复活后的 Power | Fairy/Lizard 等保命消耗与评价必须保留，不能折算成免费回复 |
| 战斗结束 | 先处理玩家复活，再 `AfterCombatEnd`、清理玩家战斗状态及战后胜利回调 | `ChosenCheese` 等上限增加与条件战后回复须独立于普通 `Heal` 审核 |

静态图包括委托和异步方法，但不能自动解析虚回调、反射或外部 Mod。312 个回调定义只完成枚举，尚未全部建立可达性封闭证明。

## 敌方、召唤物与搜索边界

- `DecimillipedeSegment`、`ReattachPower` 回复敌段；`IllusionPower` 的原生 Parafright 使用回复其敌方持有者。错误或未知玩家持有不能直接给零。
- `KnowledgeDemon` 自疗30×玩家人数，同时能通过原生固定选择创建临时状态牌。四个选择及其 Power 回调不在现有八池证明内；其后续方法已在[组件审计](native-healing-component-audit-20261003.md)复核，仍不能借敌人自疗的目标结论认证整场安全。
- `TestSubject` 设置自己的分阶段上限并治疗自己；生成 Burn 及附加 Power 的封闭范围须另审。`ToughEgg` 的孵化生命重设、`WaterfallGiant` 的自疗/巨大生命重设均是敌人目标。
- `PunchConstruct.AfterAddedToRoom` 将敌人当前生命降低至至少1；是初始化损失，不是玩家回复。
- `OstyCmd` 召唤、治疗、增加上限及复活的对象是 Osty。`Spur`、相关召唤卡、`BoneBrew`、`BoundPhylactery`、`PhylacteryUnbound`、`DevourLifePower`、`SicEmPower`、`SummonNextTurnPower` 复用该链；召唤修改、复活及召唤后回调仍须认证。
- 章节、事件、休息、奖励、读档、控制台、网络同步与多人复活不能因为“不是治疗牌”而漏扫。当前单人战斗搜索不执行房间推进/事件选项；奖励获取及多人1生命复活也不能借此扩大到多人证书。`AncientEventModel` 的满血/章节比例治疗与首领既有评价边界必须区分。
- 14 个直接生命入口事件已列入结构化清单；`DenseVegetation` 经 `MimicRestSiteHeal` 间接治疗。休息治疗的数量修改与 `AfterRestSiteHeal` 仍可触发 `StoneHumidifier`。
- `NightTerrors` 修改休息治疗，`Terminal` 入房间降低上限；未认证的 Modifier、附魔、灾厄、第三方回调或扩展继续拒绝严格认证。

## 金币触发生命上限回复：原生差分失败

审计追加核对同一 DLL 的 `HandOfGreed`、`BowlerHat`、`Ectoplasm`、`RunState` 和 `IRunState`，五次原生源码提取均成功；来源哈希记在配套 JSON，完整源码仍留在忽略目录。

`HandOfGreed` 在原生 Fatal 死亡判定后调用 `PlayerCmd.GainGold`。该命令先经过 `ModifyGoldGained` 与 `AfterModifyingGoldGained`，仅修改后金额大于0时写入金币并派发 `AfterGoldGained`。`BowlerHat` 对持有者将金额乘1.25，`Ectoplasm` 对持有者将金额置零；两者后置修改回调只产生显示效果。当前 DLL 的金币获得后原版模型覆盖为 `DragonFruit`：为持有者增加1上限，并由 `GainMaxHp` 同步治疗。单次数量可知，总触发次数未形成证明。

`AfterGoldGained` 使用 `RunState.IterateHookListeners(null)`：有效玩家永久牌组及附魔在前，随后是未熔化遗物、实际药水、Modifier、Badge、多人缩放模型；先经 `Contains` 核对，再追加 ModHelper 跑局订阅者。传入战斗子状态时则追加战斗监听者。不能把这两种监听范围混为同一表，也不能读 live 监听表来计算后台分支上界。

测试仅加入诊断夹具，运行源码未修改生产路径。Release构建0警告/0错误；`GOLD-HEALING-CALLBACK` / `88843d10d5b94471ad61d36d0efd20f4` 在约27.04秒返回 **Failed**：

| 状态 | 玩家生命/上限 | 金币 |
| --- | ---: | ---: |
| 原生与预测根 | 50/80 | 137 |
| 分支预测增加20金币 | 50/80 | 157 |
| 原生 `PlayerCmd.GainGold(20)` | 51/81 | 157 |

完整状态断言的首个差异是HP 50/51；原生加上限和回复均为1。分叉预测未改父分支或live，完整预测/实际快照保留在 `.local/general-healing-audit/gold-native-differential/`。这是原生金币命令差分；尚未运行贪婪之手整条原生出牌路线，不外推为完整战斗验收。

根的严格回复证书为拒绝、上界 `int.MaxValue`，该部分保持保守。上游“已知来源策略”资格为true、调用其零战后回复参数得到潜力0，却漏掉这条金币触发回复链；当前模拟 `GainPlayerGold` 也只增加金币。该来源不能进入零回复认证，须先补齐金币修改/回调及生命上限语义，并在缺少总次数证明时保留完整上界。

上述失败属于审计第一阶段的定位证据，原补丁和构建保留在忽略目录。后续合并 `56b6d6ee` 后补齐金币与最大生命链，正/零/负/小数金额、修正顺序、熔化、未知入口拒绝、真实 Fatal 出牌/用药、封顶和父子/live 差分已有单独通过证据，见[金币与最大生命回复链](gold-max-hp-healing-20261003.md)。该修复仍未提供 DragonFruit 总触发次数或遗物获取闭包，不能据此将未知来源上界置零。

## 尚未完成

本阶段没有把上述清单接成全模型默认安全规则。后续[组件与间接回调审计](native-healing-component-audit-20261003.md)定位全部45个原版战斗结束覆盖、18类怪物直接造牌、62种直接施加Power，并审查44项具体机制。未知回调的递归可达性、战外药水池与遗物获取闭包、全部敌人间接生成、附着效果、有限重复次数证明、源于新审计的原生/模拟严格差分，以及认证自身开销仍待完成。已知来源策略的最小原生测试通过不代表这些严格认证已完成，也不代表原始慢场景已全部提速两倍。
