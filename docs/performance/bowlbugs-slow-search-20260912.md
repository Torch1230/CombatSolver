# 盛碗虫群慢搜索：原包证据（2026-09-12）

结论：本包的首次搜索长期展开，产生大量临时对象；开始时物理内存已紧张，频繁回收后又因一次整层剪枝无法容纳而退出No-GC，随后GC暂停和搜索减速加重。导出时搜索至少持续186.2秒，尚无RESULT，不能把186秒当成最终耗时。

## 可证明的时间线

数字使用十进制GB。前61.6秒的21次显式回收合计经过29.073秒，其中记录的GC暂停约3.447秒；回收等待并不等于全程Stop-the-world。这些区间与累计GC暂停重叠，不能把29.1秒和40.6秒直接相加。

第60.6秒前平均约827展开节点/秒，随后至142.4秒约114/秒，约降到原来的七分之一。两段处于不同搜索深度、候选组合，故不能把全部差额归因于GC。日志至少明确证明，普通GC回退后暂停大增且推进明显变慢。累计分配不是同时占用140GB；上述分配/暂停来自进程级观察，包括其他线程与Mod，不能冒充独占worker计数。

## 为什么仍在扩张

原包有效策略为VeryHigh、Beam135、10万展开节点、300秒软预算、DOP16，手牌/牌堆选择限额54/42。第142秒只展开到59,501，未到这两个停止上限。主循环没有生产回合数上限，所以可以搜到40个回合层以后。这不是一个三分钟的重复重算链。

根有26张牌、三个敌人、两瓶能力药水；牌组含生成牌、抽牌回顶和自动出牌来源。它们能引入后续动作和选择组合，日志也出现原牌组以外的能力牌类型。但包内没有choice branches、各来源触发次数或完整RESULT，不能定量断言某张牌占了大多数耗时。

提前结束阈值为零战损，并保留遗物计数目标（HappyFlower当前1、目标2）。当前源码中，达标还需完整胜利、药水使用条件和遗物目标同时满足；有遗物目标时还会停用纯HP的incumbent界，以防错删目标更好的路线。该条件是值得继续量化的放大因素，尚未测出单独耗时，不等于已证明目标不可达。没有已发布结果也不等于搜索内部从未找到胜利。Royalties额度为5本身不证明根有成长目标；原牌组没有该牌，不能把设置非零误读为必定禁用早停。

当前层的ended是回合结束候选集合，并非“已找到13,498条胜利”或累计40层全量结果。一次剪枝对上万状态同时排序、分组与构建保留特征，所需的临时分配比配置的Beam135大得多。

## 源码核对及下一优化对象

- `CombatBeamSolver.Phases.cs`：主循环的节点/时间边界、每层ended集合，以及`PruneAllocationReserve`和`EnsureMemoryForIndivisibleCommit`。1.778GB是按剪枝每输入字节高水位和缓冲系数推算的保守预留，并非本次剪枝实测分配。
- `SearchGcPolicy.ResolveEffectiveNoGcRegionBudget`：Windows按当前物理压力及堆内可复用空洞计算有效预算。设置16GB不保证当时可以获得16GB。
- `CombatBeamSolver.Phases.MeetsHpTarget`、`CombatBeamSolver.Retention`：达标条件和目标存在时的纯HP界保护。
- `CombatBugReportExporter.SnapshotFieldValue`：导出期间枚举可变列表抛错，发生在慢搜索已持续186秒以后；单列为导出问题，不能解释此前减速。

下一优化应优先测量整层剪枝的中间分配、跨层保留状态以及长线候选的实际来源；在保持同一候选集合、顺序、评分及目标条件下减少物化和重复计算。若研究更强的界，须先证明对遗物计数/药水/治疗目标安全，不能直接关掉目标或缩短预算。此前选牌令牌约1%的分配削减不足以解决本包这条内存压力链。

## 剪枝探针内存边界修复（2026-09-12）

### 定位与取舍

原先把一次 Prune 中所有 EndTurn 待命探针的累计分配，作为整段不可分割剪枝的下一次预留。探针只留下四项标量，但大量瞬时模拟仍会推高预留；在小 No-GC 区域下，预留超过新区域容量就永久切回常规 GC。主搜索使用 Smart 药水策略，上一节只影响无药路径的药水谱系优化不能处理这里的主要成本。

本次改为冻结原有首次状态代表，按 Runtime 剩余内存及独占探针分配高水位分批。只有全部已派发 lane 排空后才通过 Runtime 入口回收；非探针元数据在全局排名结束、探针组前后和串行探针前后分段观测与预约，仍使用各间隔每输入分配的高水位与原50%余量。剪枝内保留 StandPatCache，防止准备阶段已跳过的缓存代表丢失；离开剪枝后恢复普通缓存释放。仍保留不可分割工作确实过大时的常规 GC 回退、取消、失败和原序提交。不改变生产 Beam、分支/节点/时间预算、排序或随机决策。

同时沿完整分配调用栈削减重复工作：

- 回合计数已经为零时不再次写零，避免分叉字典无用的写时复制；缺失计数仍写入显式零，以遮蔽根历史，非零计数仍正常重置。
- SpectrumShiftPower 的无色生成复用既有规范牌池根缓存；未命中仍走原有筛选，随机抽取与可变卡牌实例继续归分支所有。
- 卡牌附加监听器表按已知注册卡数预分配；Fork 的非空注册/生成牌表预留一个额外槽，减少首次生成/变形的整表扩容。单因素后续样本少约195MB分配；未共享可变容器。

3万节点诊断采样包含234,628个分配样本、0丢失事件；232,534个样本有确认的搜索调用栈、0缺栈。估计搜索分配24.997GB；这些是采样权重，不是逐对象精确计数。回合开始路径包含生成、变形等嵌套调用，不能将整个路径成本当成缓存的收益。零写入单因素在同一工作量下少约563MB，无色生成接入已有缓存在下一样本进一步少约1.11GB。撤回了约10MB收益的祖先链附加优化，避免扩大排序改动面。
