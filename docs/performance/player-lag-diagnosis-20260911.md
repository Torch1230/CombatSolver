## 早期会话 26356 结论

本次已确认三层后多次秒级卡死的直接原因是全进程 GC 暂停，发生在搜索、自动出牌以外的房间切换阶段。最严重的 2.82 秒长帧由一次普通 Gen0 回收几乎完全覆盖；另外三次约两秒的房间切换长帧由主线程触发的阻塞 Gen2 覆盖。不能再把这些长帧解释为单纯搜索慢、显存不足或显示条没到上限。

同时确认大量堆碎片、跨跑局旧对象存活，以及本 Mod 的一次低收益连续回收。尚无 GC root 数据，不能把全部保留对象或数百万 GC 句柄归属到某个 Mod，也不能宣称已找到并修复全部长期退化根因。本轮只取证和代码审计，没有修改游戏行为。

## 为什么更容易越打越卡

### 回收对象已经释放，空间却大量留在堆内

同一搜索的一个检查点：

- managed live 从约 5.895 GB 降到 1.502 GB，说明实际释放了约 4.39 GB 对象，并非只收走 1 GB；
- 收集完成后 HeapSize 6.140 GB、Fragmented 4.638 GB，约 75.5% 是碎片；
- committed_after_collect 13.396 GB；重启 NoGC 后进程私有字节仍约 19.11 GB。

进程占用、存活对象、堆碎片和已提交空间是四个不同量。堆里有可复用空间不代表立刻返还操作系统；背景非压缩收集随后又重启 NoGC，也可能使进程占用保持高位。这里有具体证据支持研究低频、有条件的压缩，但还没有压缩前后 A/B；不能保证每次强制压缩都更顺畅。

### 确有一次连续、收益很低的用药层回收

以录制起点为零：

- 1983.979 秒：`after_parallel_wave` 回收完成，live 约 5.469→1.143 GB，耗时 1150.5 ms，GC pause 增量 243.8 ms，重新建立分配限额约 4.85 GB 的区域。
- 1984.608 秒：`smart_potion_layer` 再次回收完成，live 约 1.222→1.206 GB，仅减少约 15.8 MB；仍耗时 477.7 ms，其中 GC pause 146.9 ms，工作集几乎不变。

代码中 `SmartLayerMemoryForecast.Decide` 只有 allocatedBytes 严格等于零才视为 fresh region；少量新分配后，如果预测下一整层放不下，仍会请求层间回收。它不区分“刚完成回收”与“确实又积累大量可回收对象”，也没有判断下一层是否本来就超过全新区域的容量。这是能具体改进的调度路径；本次详细预测决策未写入录制，不能反推该次完整 forecast 数值。

### 旧对象与句柄的保留现象仍然存在

- 第 1 段最早一次 HeapStats：166,851 个 GC 句柄；第 1 段末约 281 万；第 7 段开始约 378 万，末尾 4,102,153。它们是 CLR 的 GC 句柄，不是任务管理器的 Windows 句柄数。
- 最后一条帧记录仍观察到 3 个跑局、52 个战斗、1 个结果对象存活。最早战斗存活约 35 分钟，经历 327 次 Gen2。观测器只用弱引用，并未通过这些槽持有对象。
- 以上证明保留现象需要继续追根，不能仅以“多收一次”解释。普通分配 trace 不包含这些对象的完整根链，尚不知道全部持有者；不能把弱引用存活直接写成已定位某个 Mod 的泄漏。

## 包装对象与界面开销

第 7 段弱登记相关分配抽样仍能看到：

- `RichTextEnvironmentLifetimePatch.CaptureEnvironment → RichTextSine`：WeakReference 抽样权重约 24.44 MB，登记字典节点约 41.64 MB。

RichText 的现有补丁确实 Dispose 环境字典；调用栈仍有分配不代表此前修复失效，它没有消除包装和 WeakReference 的创建。分配抽样金额不是对象精确个数、存活量或 CPU 比例，不能据此将全部 410 万句柄分给某一条调用链。NodePool 的清理生命周期值得修正，但也尚未做输出与信号行为的等价验证。

## 录制自身影响

帧窗口中的上下文/引擎采集最大约 4.68 ms；每分钟程序集与补丁清单采集后半段有约 0.25—0.63 秒的经过时间（全程最大约 0.724 秒）。这些计时会包含 GC/调度等待，不等于录制器独占 CPU。录制自身可能增加个别长帧，不能忽略；但上述四个主要卡死已由独立的 CLR 暂停事件覆盖，不能仅归为清单采集。后台进程采样亦有被暂停影响的长耗时。

## 修复顺序建议与验证边界

1. 先修本 Mod 的层间重复回收判定：使用真实回收周期与回收后工作量，区分可通过回收腾出的空间和整层本来就超过区域容量；继续保留每批工作准入。
2. 处理已确认的原版临时包装生命周期，减少依赖终结线程的清理；先验证节点回收、信号解绑与文字输出等价，不能直接删除原版回调。
3. 再评估高碎片时在安全边界进行一次压缩，并让之后的普通 GC/房间加载承担更少工作。不要将每个自动检查点都改成更重的阻塞回收，也不要直接禁止原版 GC。
4. 旧跑局/战斗的实际强引用链仍是缺失证据。下一步取证必须避免重用曾挂起长局的 Ctrl+F8 dump 方式；本次没有触发转储，也没有要求玩家重打一局。

结论是“主要秒级卡顿已定位到昂贵 GC，重复回收与大碎片已证实，累积对象的完整持有链未确诊”，不是“所有卡顿已修好”。
