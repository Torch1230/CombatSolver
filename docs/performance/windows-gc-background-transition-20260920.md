## 根因与实现

旧检查点先 `EndNoGCRegion`，再创建后台收集完成哨兵并请求后台Gen2。在大区域刚结束、旧分配额度恢复后，这个间隔允许其他线程的分配触发前台收集。实验中只提前设置 `SustainedLowLatency` 仍在区域退出阶段观察到5.876秒暂停；因此仅改变延迟模式不足以修复。

Windows 检查点现在先在区域内准备完成哨兵，然后直接请求非阻塞、非压缩Gen2，由CLR的诱发收集结束该区域，消除上述单独退出步骤。进入区域前暂用 `SustainedLowLatency`，让CLR在诱发退出后恢复此模式；Runtime另外保存调用者的原模式，取消、回退和最终退出时恢复。等待自己的收集完成、哨兵确认、超时排空、手动请求和引用释放epoch规则保留。主动退出计入NoGC结束而不计为意外丢失；结束尝试既包括显式结束也包括检查点的诱发结束。

参考 [.NET 9 GC实现](https://github.com/dotnet/runtime/blob/v9.0.9/src/coreclr/gc/gc.cpp) 中诱发收集与NoGC状态恢复、以及[延迟模式文档](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/latency)。实现源码用于解释机制，暂停收益来自本机Windows实测；系统内存压力仍可能使CLR执行阻塞收集。

第二个问题是重新预留大区域本身暂停托管线程。12GB直接后台退出实验的EventPipe跟踪显示后台Gen2成立、无丢事件，但两次区域重建的 `SuspendEE`→`RestartEE` 分别为375.157ms、124.769ms，`GetTotalPauseDuration` 却未计入它们。因此另将Windows单次预留限制为4,000,000,000字节，较小用户预算保持不变；此上限贯穿首次准入、重建和有界恢复。设置保留玩家输入，中英文说明提示Windows上限。它不是托管活堆或进程内存上限。

新区域的物理余量不再加上全堆 `FragmentedBytes`：这些洞并不能证明NoGC所需SOH段可复用。普通搜索内分配的复用估算仍保留；这里只收紧新预留。保留已有不可分割提交窗口判断、低余量回退和恢复迟滞。

进入区域前还确认后台GC就绪：先在小堆上请求并等待已完成后台收集；若首次退回前台，再尝试一次，仍不支持并发则本次不建立大区域。10秒内本策略确认过的后台完成证据可以复用，尝试次数有界，用户关闭或平台不支持时不执行。这发生在独占准入Gate内、scope计数之前，收集自身不等待Gate或搜索退出。取消等收集排空后检查，原延迟模式在finally中恢复。

原因由追加的EventPipe诊断明确缩小：Windows工作站CLR的后台线程在23,092.652ms处退出，首次大检查点在34,198.396ms处重新创建线程；该次GCStart虽标为BackgroundGC，GlobalHeapHistory与实际完成指标却显示阻塞压缩，线程暂停1.519秒。后续后台回收正常。该trace尾部因进程结束而截断，采用显式partial转换，只用于这段完整事件序列的诊断，不当作全请求最大值证明。源码中后台线程/标记准备失败会回退阻塞，不能把GCStart的请求类型当成完成类型。

Windows搜索结束后异步后台回收自己的区域，不再把大年轻代保留到玩家下次操作。这样避免后台线程再次空闲退出后才清理大堆；手动压缩、引用释放epoch与独立完成链保留。其他平台继续原战斗级保留策略。中英文设置说明同步这一差异。

## 探索与未采用方案

- 关闭NoGC：30秒配置下请求35–36秒、约16.6秒累计GC暂停，吞吐下降，未采用。
- 仅限制1GB、仍先显式结束：22次重建，最大暂停1.407秒，未采用。
- 全程普通GC配合SustainedLowLatency：最大暂停约58ms，但工作量和吞吐下降；当时NoGC配置断言失败，不能算通过，未采用。
- 仅提前设置SustainedLowLatency：大区域退出仍暂停5.876秒，120秒启动器超时，未采用。
- 12GB直接诱发退出：六次完成回收均后台，搜索GC最大57.586ms；游戏内部结果Passed但启动器120秒超时，按诊断样本处理，不计入完成性能样本。跟踪还揭示上述预留停顿。
- 4GB直接退出但未确认后台就绪：正式候选一次首检查点仍阻塞1.468秒；追加诊断复现1.519秒，因此没有作为最终修复交付。
- 2GB直接退出：最大GC16.746ms，但30秒内仅253,105转移；4GB探索为341,949转移、最大20.262ms、六次重建0.1–3.0ms，因此选择4GB继续正式验证。二者是选型样本，不是最终对照。

原包恢复ContinuationStamp通过，但旧包缺少模型编号映射，`nativeStateVerified=false`；不把它写成完整二进制原生恢复。独立生命周期场景 `6a17bd7aa3f4416fa57d94cde6345400` 在30.84秒内Passed，包含八项观察顺序、后台确认/重启、取消/晚手动、超时排空、原手动吸收、故障以及两种释放epoch时序合同。Windows独立checkpoint、commit-window、recovery-lifecycle、scopes通过；最后的Windows/Linux共享background-tail四项和Linux基础27项/checkpoint通过。Release构建0警告0错误，两端结构门禁通过。

验证过程保留失败：首次游戏生命周期夹具发现诱发退出后的区域状态要在确认等待之前同步，已修复。Windows正常退出会清理一次新区域，因此更新对应次数预期，仍保留scope内不得额外安排手动回收的断言。后续两次夹具触及120秒；独立CLR合同与线程栈定位到故障路径在finally读取默认 `GCMemoryInfo` 时再次抛异常，使手动/检查点完成源未结算而永久等待。改为可空采样后，Windows游戏内八项检查与Windows/Linux独立尾部四项检查全部通过。此前将无日志误判为NCombatRoom建局停滞，最终证据纠正为上述故障完成链问题。未提高启动器超时。

搜索结果配置断言等待Windows已发起的异步清理完成，再核对曾建立预算与稳定结束状态；该等待不请求额外GC。
