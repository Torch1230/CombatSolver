# 快照内部按需读取与局部复用（2026-09-12）

本轮遵守“不重写另一套战斗模拟器”：仅修改现有 `StrategicEffectContext.Build` 的一个关键字读取点及两个消费者。卡牌、Power、回合模拟、Fork、状态键、排序公式和生产搜索预算均沿用现有实现。

## 为什么选这里

此前 `8faa771` 的真实 CPU 栈中，策略上下文构造包含3,850个机甲搜索样本中的189个、26,982个亡灵搜索样本中的2,208个。其关键字读取子调用分别有155／1,385个样本（约4.03%／5.13%的全部可确认搜索CPU）；牌堆查询子调用134／1,132个，彼此重叠，不能相加。新基线 `77d359c` 仅比该采样版本优化快照释放，策略上下文实现与这条子路径未变化；这些历史直接样本用于定位，后面的收益来自新基线 A/B，不冒充本轮重新采样。

实际游戏程序集的 IL 显示：`CardModel.Keywords` 调用 `GetKeywordsWithSources(All)`；战斗路径创建关键字集合、复制本地关键字，并交给 `ModifyKeywordsInCombat`。因此，读取“是否消耗”不只是读取一个字段，可能涉及集合分配、Hook分发和牌堆定位。IL只说明原生入口，已安装补丁后的实际成本仍以真实搜索为准。

原策略上下文对每张牌都先查询消耗关键字，之后只有三个用途：

1. 请求 `ExhaustPlays` 时计算消耗牌数；
2. 请求小刀供应/攻击次数且当前牌为小刀时，区分可重复使用与一次性；
3. 当前牌实际生成小刀时，区分一次性生成器。

仅要求攻击次数、格挡技能数、剩余回合等信息时，大部分牌的消耗关键字结果没有消费者。尤其非小刀、也不生成小刀的普通牌，仅因开启攻击次数估值而读取关键字没有价值。

## 复用范围与失效证明

- 每张牌每次进入 Build 循环都重新创建一个可空布尔局部变量，初值未知。
- 只有当前需求及实际卡牌机制需要时，才读取完整 `Keywords` 的 `Exhaust`；每张牌每次至多读取一次。
- 复用期间只有该张牌的只读元数据、数值和纯 `CardMechanismFacts` 计算；没有动作结算、`MutablePreview`、牌堆移动、Power写入或Fork。
- 离开该卡循环体即结束缓存生命周期；下次 Build 重新读取，哪怕使用同一张牌对象。无需版本号、失效通知或新增模型字段，也不会把引用带到兄弟分支。
- 牌自身的消耗关键字与“技能因效果而消耗”继续区分：后者影响消耗次数与一次性生成器，但不冒充小刀自身的消耗关键字。
- 卡牌类型、生成小刀事实、分数公式、需求标记和返回记录字段不变。第三方类型继续使用原来的机制旁路；注册接口没有变化。

## 放弃或暂未采用的切口

- 有序/无序牌堆指纹已经有现成缓存，并非每次都重算。无序累加调用链在原样本中仅约0.18%／0.13%；合并循环还要处理禁用缓存的第三方附属模型，本轮未增加这层复杂度。
- Fork 已共享只读存储、复用映射数组并按引用重映射缓存；不能删掉需要隔离的对象复制。本轮未修改 Fork。
- 归一化不仅施加效果，也清除旧效果和识别新生成牌；没有用“当前Power为0”跳过全牌扫描。

## 验证方法

`tools/StrategicKeywordChecks/run.py` 提取生产上下文构造，只反向恢复本次关键字改动形成对照算法。134,930组案例比较完整返回记录，覆盖65,536种需求位组合、技能消耗与自身消耗、小刀/生成器、第三方类型、空牌组及两次Build之间修改同一批牌，全部通过。关键字读取数1,551,651→824,992仅是该测试语料的机制计数，不是游戏收益数字。模型替身只提供可控属性；真实挂钩行为由后面的固定无头场景作代表性检查，不声称覆盖所有第三方关键字来源。反向还原出的对照方法已与修改前保存的实际源码逐字核对一致。

候选 Release 编译0警告/0错误，Linux结构门禁通过（search_files=87）。正式测量使用 A-B-B-A；每个新进程先预热两个场景，再正式测各一次。基线为77d359c产物，候选只修改上述读取逻辑。机甲normal VeryHigh，亡灵Low FixedBudget，DOP8、No-GC16GiB，每请求总超时120秒，首次求解结果后停止。没有启动可见Steam，也没有改生产预算来取得收益。
