# GC 完成链修复与优化筛选（2026-09-21）

替代已关闭的 #116 / #120，基线为上游 `3f4002bd`（0.43.2）。本轮重新构建和测试，不沿用旧 PR 的性能数字。最终仅保留 GC 完成链卡死修复；两项分配优化均已从提交中撤掉。

## 独立保留：异常后不再永久等待

GC 检查点、后台回收和区域退出的诊断可能抛错。旧代码可能在释放活动标志、完成等待任务之前退出；后续搜索、deferred 回收或排队手动 GC 因而一直等待。

修复限定在 `SearchGcPolicy` 的失败收尾：无论诊断或收尾是否失败，都终结所属完成源；登记/提升失败撤销未派发状态并通知相关等待者；操作和收尾同时失败保留两个原异常。原错误仍向调用者传播，后续显式请求可以继续进入。

- 上游源码运行新增检查点夹具，在 12 秒截止时取消；中间版本漏结清排队手动请求，同样由独立提升夹具复现超时。修复后这两条以及其余故障路径均通过。
- Linux 与 Windows 的真实 CLR 检查各 **54 项通过**：基础 26、scopes 8、recovery 9、recovery-lifecycle 2、checkpoint 1、diagnostic-failure 8。
- 新增 8 项包含检查点、后台开始/结束、区域退出、请求登记、deferred 登记/提升、双重异常；验证原异常身份、任务终结与下一次搜索准入。日志注入仅在工具替身中，不增加生产测试 API。
- Release 构建成功；Bash / PowerShell 结构门禁通过（`search_files=205`）。

保留上游 Windows 预算与 GC 准入、回收/恢复政策；不带入 4 GB 上限、预热、搜索末尾回收变更或大型生命周期重构。这是有失败基线的可靠性修复，不宣称缩短正常 GC 暂停。

## 性能筛选方法

Windows 11 / .NET 9.0.19，独立静音无头进程；每场两份基线、两份候选，交错运行。固定 DOP 8、配置 No-GC 12,000,000,000 bytes、搜索 60 秒和既定节点/Beam，单请求上限 120 秒。未扩大预算，也未开启增量验证。

花园使用原问题包的 start 检查点（私有归档仅记录 SHA-256），另外两场使用仓库固定生成场景 `coverage/novelty-search/dev-02-defect-elite.json` 和 `sentinel-discard.json`。对比请求总展开/转移、非时序搜索指标、完整记录路线、开局/配置/牌组与回放政策。工作集采用操作系统进程峰值；Private Bytes 约 500 ms 采样，包含启动/建局/搜索/清理，不等于搜索独占内存或分配量。

### 撤掉组合候选

第一轮候选为卡死修复 + 根怪物意图缓存 + Skittish 临时分配削减。三场 ABBA 共 12 份有效搜索、6 对对账无差异。

| 场景 | 搜索耗时 | Worker 累计分配 | 进程峰值工作集 | 采样 Private 峰值 |
|---|---:|---:|---:|---:|
| garden | -4.38% | -3.25% | +13.09% | +25.93% |
| defect-elite | +2.24% | -0.86% | +5.08% | -9.10% |
| silent-discard | +5.97% | -1.75% | -1.13% | +6.21% |

变化为两份候选均值 / 两份基线均值 - 1。根缓存的独立收益不能从组合数据推出；组合在花园的内存代价及两个哨兵的耗时退化不足以支持保留，因此撤掉缓存，再单独筛选 Skittish。组合的 7 项原生对照虽通过，也不能替代性能收益。

另有一份 defect-elite 基线因系统内存压力未建立 No-GC 区域，触发既有测试断言；保留为失败样本，不计入均值。系统负载 29,558,452,224 bytes 高于运行时上限 29,228,695,790；相同输入重跑通过。未关闭其他用户进程，未降低或放宽测试断言。

### 单独筛选 Skittish

撤掉缓存后，固定相同输入，以 D1/A3/A4/D2 顺序重新跑两场，共 8 份有效搜索、4 对对账无差异。两项 Skittish 原生状态差分通过，覆盖首击完全格挡不能改看后续命中，以及首击受伤才获得格挡。

| 场景 | 搜索耗时 | Worker 累计分配 | 进程峰值工作集 | 采样 Private 峰值 |
|---|---:|---:|---:|---:|
| garden | -3.24% | -0.91% | +9.01% | -4.41% |
| silent-discard | +9.09% | +0.02% | +0.22% | -2.23% |

花园分配收益很小，伴随工作集峰值增加；无关的弃牌场景两对耗时分别 +2.17% / +15.97%。共享主机和 GC 波动使这些结果不能证明 Skittish 必然导致退化，但同样不足以证明值得增加生产改动，因此 **Skittish 也撤掉**，不继续为通过验收挑样本或调预算。

这轮花园的最大 GC 暂停：基线两份 19.108 / 1914.553 ms，候选 2336.166 / 1767.094 ms。独立卡死修复解决异常后永久等待，不解决正常回收的秒级暂停。

最终源码回到上游 + `10e52b1c` 的 GC 修复，以上 20 份性能样本仅用于解释撤回取舍，不能算作最终纯修复版的性能验收。最终版本 Release 构建通过（0 warnings / errors），游戏搜索冒烟 Passed（`bed2628af2e94abd843a0c45103bbc05`）：17,600 展开、214,161 转移、战损 1，与同批上游 A3 的非时序指标、完整记录路线和回放政策对账无差异。单样本不是性能验收；最大 GC 暂停仍为 1645.559 ms。CLR 工具链接的 GC 源码未变，复用已通过的双平台 54 项，不重复计数。
