# 局部字段与数据结构的内存优化研究

**找到了两个值得继续验证的小切口：状态仓库的辅助类型计数表，以及 ForkableList 的内部存储包装。** 它们不要求新增战斗语义、重写 Hook 或切换搜索后端。本轮只提交研究工具、原型生成器与证据，生产 `src` 没有改变；下面的字节数是独立 .NET 分配测量，不是整场搜索或 RSS 改善。

这也是对[长期维护成本研究](simulation-maintenance-review-20260912.md)的进一步收紧：当前优先寻找字段、容器与分配层的小改动。逐状态族迁移只保留为远期方向，暂不把它或完整 Compact 闭包作为下一批默认实现。

## 1. 测量范围

源码基线 `2f5a6df`，SDK 9.0.120，运行时 .NET 9.0.19，Linux x64，Release，`DOTNET_TieredCompilation=0`。通用布局探针每个形状先预热 1,024 次，再测五块、每块 10,000 次；五块的每操作分配一致。对象经过静态引用发布，防止分配被消除；采用线程累计分配计数，不依赖 `Marshal.SizeOf` 推算托管对象。[探针与复现](../../tools/DataLayoutProbe/README.md)、[完整 JSON](simulation-data-layout-20260912.json)。

状态仓库另复用已有 `PredictionStateStoreChecks`，生产源码和独立候选分别编译，显式开启类型计数检查。每种仓库测 10,000 次 Fork，重映射替身复用并预热；这里只包含仓库及测试状态的分配，不包含完整模拟器、游戏模型克隆、搜索和 UI。两次短计时样本均保留在 JSON，但不据此宣称 CPU 加速。

最初一次基线使用默认分层编译，空仓库多出 128 字节固定噪声，且配置与候选不同，因此未进入正式比较；随后用相同关闭分层编译配置测量基线。报告中的基线与候选配置一致。

## 2. 只缩窄字段，哪些确实省内存

| 被测内容 | 当前形状 | 缩窄后的形状 | 实测结果 |
|---|---:|---:|---|
| 单个 Counter 类：一个 int → short | 24 B/对象 | 24 B/对象 | 不省；较小字段仍落在同一对象大小 |
| 一个 int 的 class → 装箱 struct | 24 B/对象 | 24 B/对象 | 不省；object 容器仍需装箱 |
| 三个引用、两个 bool 的卡牌包装形状 → byte flags | 48 B/对象 | 48 B/对象 | 不省；对象对齐后大小相同 |
| Dictionary 的 `(object, Type)` 键 → `(object, byte)` 键 | 16 B/键 | 16 B/键 | 不省；引用与填充仍占空间 |
| Dictionary 的 `object → int` 条目 → `object → byte` 条目 | 24 B/条目 | 24 B/条目 | 不省；Entry 的整体大小相同 |
| 64 个元素的 long[] → int[] | 536 B | 280 B | 数组本身省 256 B，约 47.8% |
| 1,024 个元素的 int[] → short[] | 4,120 B | 2,072 B | 数组本身省 2,048 B，约 49.7% |
| 1,024 个元素的 bool[] → BitArray | 1,048 B | 184 B | 该完整 BitArray 对象图省约 82.4% |

表中的 Wrapper 是按当前 `PredictedCard` 三个引用、两个 bool 构造的合成形状，并非直接测量游戏程序集实例。Dictionary Entry 的大小来自本次实际运行时；这些字节数不构成跨运行时、平台或任意对象布局的永久保证。

**连续数组最容易兑现字段缩窄的收益，小对象和字典往往不会。** `bool` 字段改成 `byte` 本身也不是位打包；BitArray 节省大量元素时的容量，但有自己的对象/数组开销和位操作成本。64 个 bool 的样例仅从 88 B 降到 64 B，不能用“一个 bit 替代一个 byte”直接宣称整个对象缩小八倍。

C# 数值范围和装箱机制可核对 [Microsoft 整数类型文档](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/integral-numeric-types)与[装箱文档](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/types/boxing-and-unboxing)。表中对象大小则以本地实测为依据。

### 本项目不能随意缩窄的字段

现有 `CreatureVitals` 允许最大生命和格挡达到 999,999,999，探针直接调用生产代码验证了这一范围，`ushort` 的 65,535 无法容纳。[源码](../../src/Engine/InCombat/Simulation/Compact/CreatureVitals.cs)。费用和 Power 还可能包含负值；只观察常见对局数值小，不能证明窄类型安全。

Compact 的 `long` 槽也不是全部只装一个小整数。`CardInstanceValue.Data` 的低位保存定义与附魔标志，高位保存 X 与关键字；RNG 需要完整 64 位状态。探针验证了含大 X 与关键字的生产编码往返，转成 int 会丢失数据。[实例编码](../../src/Engine/InCombat/Simulation/Compact/CardInstanceValue.cs)、[值 RNG](../../src/Engine/InCombat/Simulation/Compact/ValueRng.cs)。

因此不能直接将整个 `ReversibleValueState` 的 long[] 改成 int[]。未来可研究在冻结时按页选择 int[] 或 long[]、读出还原成 long，保留宽值回退；但这需要先测实际页内范围与宽值混入比例，并计入捕获扫描、恢复分支和页共享成本。本轮没有实现或验证这种自适应压缩。

## 3. 首选小切口：仅替换类型计数辅助表

`PredictionStateStore` 当前有三个主要字段：保存权威状态的 `_states`，模型别名 `_modelAliases`，以及用于快速判断某类状态是否存在的 `_countByType`。主状态值已经直接存入字典，没有额外的 entry 包装对象可再删一层。[源码](../../src/Engine/Common/PredictionStateStore.cs)。

候选只把第三项从 `Dictionary<Type, int>` 改为 `List<KeyValuePair<Type, int>>`，调整计数读写与 Fork 拷贝。主表结构、可变状态对象、立即 Fork、引用身份、alias 和重映射全部保留。变更只限同一个源文件，可由[候选生成器](../../tools/DataLayoutProbe/make_state_store_candidate.py)产生独立源码及 patch；它不会修改生产源文件。

| 独立仓库样例 | 原版 B/Fork | 候选 B/Fork | 减少 |
|---|---:|---:|---:|
| 空仓库 | 40 | 40 | 0 |
| 1 个状态、1 种类型 | 520 | 424 | 96 B，18.46% |
| 16 个状态、1 种类型 | 1,384 | 1,288 | 96 B，6.94% |
| 16 个状态、2 种类型 | 1,384 | 1,288 | 96 B，6.94% |
| 16 个状态并有模型别名重映射 | 1,992 | 1,896 | 96 B，4.82% |

生产与候选的已有合同检查均通过：读取/Peek、类型计数、删除与重新添加、父兄弟隔离、插入与交错类型顺序、模型 alias、共享状态只分叉一次、事务边界和失败传播。候选构建明确传入 `CHECK_ENTRY_COUNTS`，没有因为覆盖源码而绕过这组检查。

**这证明辅助小表能省一笔确定的局部分配，不证明整场省 18.46%。** 节省量取决于不同类型数量、容量增长和空仓库比例；当前样例只有一至两种状态类型。线性查找在类型很多时可能变慢，`HasEntries` 又是热入口，应先确认真实类型数分布，再做固定工作量比较。该候选暂不进入生产，也没有重做通用 COW 或对象别名规则。

如果真实负载中一百万次 Fork 都符合本次非空小表形状，机械换算为少分配约 96 MB（十进制）；这既不是已测搜索收益，也不是同时少占 96 MB 内存。类型表很大时，这个换算不成立。

## 4. 第二个小切口：合并 ForkableList 的包装对象

当前结构为 `ForkableList → Storage → List`，Storage 只保存 List 引用和共享标记。研究候选让私有 Storage 继承 List 并保存同一个标记，变成 `ForkableList → Storage/List`，保留共享后首次写入复制的方式。这里减少的是一个分配对象，不改变列表元素的宽度。[当前源码](../../src/Search/ForkableCollections.cs)。

| 操作 | 原版分配 | 研究候选 | 减少 |
|---|---:|---:|---:|
| 构造空 ForkableList | 88 B | 64 B | 24 B |
| 从 16 个 int 构造 | 176 B | 152 B | 24 B |
| 普通 Fork，共享存储 | 24 B | 24 B | 0 |
| Fork 后首次修改已有元素 | 176 B | 152 B | 24 B |

测量直接链接生产 ForkableList，候选仅存在于探针。父/兄弟分支隔离、分叉后旧枚举器仍读取原存储、缺失元素删除、独占修改使旧枚举器失效等检查通过。

本轮候选只实现了测量所需操作，尚未覆盖生产 Insert、RemoveAt 等全部入口及实际并行场景，因此没有直接替换生产类型。它也不减少每次普通 Fork 的 wrapper 分配；不能把所有 Fork 次数乘 24 B。只有实际构造存储或发生首次写入复制的次数才对应这笔收益，合并 Dictionary/HashSet 包装需要分别审计其构造和枚举路径，不能自动照搬。

## 5. 为什么暂不替换主状态字典

对相同的预先存在键和值，主字典与仅含 `(Model, Type, State)` 的数组分配如下。数组没有提供字典操作，数值只用于辨认索引与容器成本。

| 条目数 | Dictionary 构造并填充 | 恰好长度的条目数组 |
|---|---:|---:|
| 1 | 240 B | 48 B |
| 4 | 384 B | 120 B |
| 16 | 744 B | 408 B |

这些数字不能当作等价替换的收益：数组还缺增长、查找、删除槽复用、别名移动、计数及原枚举顺序。直接改成追加列表可能改变“删除后重新加入”的位置；按 Model 分组又可能改变跨类型遍历顺序。既有合同专门覆盖这些行为。

同样，`object` 改成 `IPredictionStateForkable` 仍是引用字段，不会自动把状态内联；class 改 struct 放进 object 仓库仍会装箱，并可能改变现有可变借用行为。给主状态表建立类型索引、稳定实体编号或分族内联存储，已经比辅助计数表替换大得多。当前先保留其精确语义。

## 6. 如何保留最大比例的既有优化

保留现有 Preview COW、不可变历史、集合共享、Fork 身份重映射、原搜索排序与预算，以及已完成的公共算术和正确性修复。小改动应只去掉多余的容器开销或无用容量，而不牵动这些合同。

历史完整亡灵分配采样中，`PredictedCard` 约 4.163 GB、其引用数组约 3.435 GB、Int32[] 约 2.813 GB；这些是累计分配采样估计，不是存活堆，也不是当前版本结果。小 bool 压缩不能消除前者；数组元素缩窄也不能直接消除对象引用。[原剖析](simulation-profile-20260910.md)。

原 `PredictionStateStore.Fork` 的 CPU 占比约为请求的 0.58%，只说明它不是主要计算热点；**不能拿这个 CPU 数字否定内存优化，也不能拿 18.46% 的局部内存下降宣称大幅提速。** 本轮的辅助小表实验正是把两种判断分开。

下一批若进入生产实现，优先测辅助类型计数表的真实类型数及查询频率，再在固定工作量下比较完整分配与时间；有收益才接入。ForkableList 包装合并独立成批，不与小表同时修改，以便归因。优先级更低的页宽压缩只在真实数据范围足够集中时研究，不压缩 RNG 或截断实例身份。

没有证据证明这两个切口能保留 Compact 在闭合域的全部约 47% 分配收益；那部分收益涉及更多对象图、执行和恢复机制。当前可以确认的是：存在无需迁移战斗规则的局部机会，并已用实际字节数筛掉了一批看似简单但无收益的改法。
