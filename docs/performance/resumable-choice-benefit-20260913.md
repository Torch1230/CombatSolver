# 可恢复选牌的理论收益模型

本轮只计算理论收益，不修改生产语义、不重跑相同场景。结论：现有四张牌自身选牌前缀的直接收益更接近百分之几以内，不支持十倍提速。推广到回合开始、嵌套和自动出牌后可能增加收益，但目前缺少各暂停点可删除前缀的CPU数据，不能给出可信总收益承诺。

## 输入与限制

- [前缀普查](resumable-choice-research-20260913.md)：3b91d22研究基线，第二轮run `ebf379e1a6494fe893495be05cfaddf6`，固定20000节点单主搜索，完整结果与无插桩对照一致。
- 历史CPU采样：2352d08，26683条搜索样本，手动出牌占搜索CPU 6.2212%。该采样早于后续快照优化与稳定回合前缀优化，不是当前版本精确占比。
- 无插桩参照：已有回合前缀优化B1/B2均值21.257258秒、16.365232188GB分配、2.284715秒GC暂停。它仍是20000节点、禁用两药水槽的局部对照，不能外推完整100000节点请求。
- [模型输入](resumable-choice-benefit-inputs-20260913.json)、[计算结果](resumable-choice-benefit-20260913.json)、生成器 `tools/ChoiceContinuationProbe/estimate.py`。原CPU/ABBA来源位于#90的女王性能研究；这里只保存本模型所需标量，不把不同基线描述成同一次实验。

CPU模型额外假定：同一卡牌/资格类中首次与重复访问的平均前缀成本相等；累计scope时间比例近似CPU成本比例；跨提交阶段占比近似不变。实际scope包含调度/GC影响，CPU分类还有优先级排除，故以下是条件计算，不是实测、统计置信区间或严格上界。若CPU占比假设变为一半/两倍，CPU估算也相应减半/翻倍。

## 先扣掉每个动作不可省略的第一次

对每张牌：

`重复前缀估算成本 = 测得前缀总成本 × (访问数 − 动作族数) / 访问数`

再估CPU份额：

`f = 6.2212% × 重复前缀累计scope时间 / 全部ManualPlay累计scope时间`

这个分母为28.915秒累计scope时间，不能直接拿它与21.257秒墙钟相除。以上换算先在同类scope内求比例，再使用独立CPU采样权重。

| 覆盖范围 | 假定可消除重复访问 | 估算减少分配 | 占参照worker分配 | 未扣恢复成本的CPU减少 |
| --- | ---: | ---: | ---: | ---: |
| 单张DAGGER_THROW，严格初筛 | 16378 | 165MB | 1.01% | 0.24% |
| 四张牌，严格初筛 | 39559 | 337MB | 2.06% | 0.52% |
| 四张牌，所有已观测形态均支持 | 120079 | 1043MB | 6.37% | 1.83% |

最后一行需要覆盖Adroit、Bound、重复出牌、活动成对状态等，且假设同族访问都能共享有效前缀，明显比当前首个原型范围大。初筛通过本身也不等于暂停Fork合法。这张表不包括通用嵌套/回合流程。

## 保存与恢复的盈亏平衡

每个动作族有n次选择回放，前缀P、后缀S、原始父状态Fork为F；保存一次暂停帧为C，每个兄弟恢复成本R，从暂停状态Fork为F'。

- 原成本：`n × (F + P + S)`。
- 采用暂停后的近似成本：`F + P + C + n × (F' + R + S)`。
- 差额：`(n−1)P − C − nR − [nF'−(n−1)F]`。

首次探测和首个兄弟能否复用状态会改变一个Fork常数项，不能默认忽略。关键是F'取代了F，独立兄弟的Fork没有凭空消失；后缀、完整结果快照、估值与原序提交仍需执行。

若把全部新增成本折算为吃掉前缀毛收益的一半，前三行CPU净减少分别约0.12%、0.26%、0.91%；若成本吃满则无收益，超过则回退。这是成本敏感性，不代表“预计能保留一半”。分配也要单独计账：单卡平均每次可删重复访问约10KB分配，活动历史复制、载体及Fork差额要从中扣除；保存状态的峰值存活量可能上升。

## 换成耗时意味着什么

使用 `T新 ≈ (T旧−G旧) × (1−f净) + G新 + 额外墙钟开销`，还必须假定CPU减少能按比例缩短关键路径、并行效率不变。CPU占比不是串行墙钟份额，实际收益可能更低，甚至回退。

以21.257秒参照、GC仍为2.285秒、恢复零成本为例：

| 范围 | 条件模型中的新耗时 | 缩短约 |
| --- | ---: | ---: |
| 单卡严格初筛 | 21.21秒 | 0.05秒 |
| 四卡严格初筛 | 21.16秒 | 0.10秒 |
| 四卡所有形态 | 20.91秒 | 0.35秒 |

因此不应把1GB少分配直接翻译成数秒CPU收益。

GC存在非线性机会：若减少分配恰好让这次搜索不再触发某次长暂停，可能额外省掉那次暂停。参照全部GC暂停约2.285秒；极乐观地把它全部删掉，四卡模型约18.63秒，即缩短约12.4%。这不是预测：NoGC有不同堆段预算、运行时与探针开销、后台分配及存活对象约束，worker总分配低于16GB也不保证不发生GC，减少1GB更不保证少一次GC。不能把这份机会加到每个样本或完整请求中。

## 如果做成更广的执行器

历史“选择回放调用栈包含54.78%的搜索CPU”包括Fork、快照、后缀等不可全删工作，而且已有回合前缀优化已减少其中一部分。它只适合作非常宽松的敏感性参照：

| 假设真正删掉该历史调用子树的比例 | 搜索CPU减少 | 理想CPU加速比 |
| --- | ---: | ---: |
| 10% | 5.48% | 1.058倍 |
| 25% | 13.70% | 1.159倍 |
| 50% | 27.39% | 1.377倍 |
| 100%（执行语义上不可实现） | 54.78% | 2.211倍 |

这些比例不是覆盖计划的预测。特别是“支持了一半选择来源”不等于“删除了一半子树CPU”，仍要扣首次前缀、每个选择的尾部、Fork和快照。也不能把历史回合前缀收益再次相加。

21.257秒降到10秒需减少约52.96%墙钟；原完整请求在120秒上限内未完成，降到10秒需要超过91.67%的请求总耗时削减。两者都是算术门槛，不以20000节点线性外推100000节点。当前四卡测量离这些门槛很远。

## 后续研究的选择

先增加回合开始及嵌套选择的“共同前缀CPU/首次与重复成本/Fork差额”诊断，才能判断广覆盖是否有5%、15%或更大空间。已有稳定回合前缀必须排除，避免重复算收益。只有显著的剩余可删除CPU被定位后，扩大执行器支持面才有成本依据。

若先做单卡原型，应把它定位为所有权与正确性验证，验收最关键的是续接/Fork额外成本是否低于可删前缀；目前没有依据把它列为达成10秒目标的主要手段。
