# PR #129：上游整合与极高配置复测（2026-09-23）

本轮完成上游整合和重新评测，但 PR 保持草稿。已验证的显著收益在计算期内存，
没有证明额外 20% 提速或决策改善；部分场景有明显耗时回退，不能按原先的小代价假设作正式交付。

## 范围

本轮从已提交的 PR 头 `8748c8da` 建独立整理分支，合入上游 `68700c23`（0.45.0），
合并提交 `09dc002`。未将随后大量实验档案和已撤回原型并入 PR。
最新上游的构建作为 A，合并后的最终候选作为 B；旧版 High/DOP1 数字不计入本轮收益。

保留的生产行为：在已排空的 solver / 完整回合层边界回收临时对象；搜索结束后清理进度引用；
怪物状态空/单项指纹省去排序；稳定有序变异义务的判重标识；开局前缀续搜保留真实动作历史。
本轮新增的代码限于验证工具与测试夹具，没有追加未经测量的游戏方法补丁。

## 测量口径

- 17 个固定根：五角色各覆盖精英、首领、普通遭遇，另加女王、实验体高压根。
- VeryHigh、300,000 ms、节点配置 500,000、Coordinator、生产预算、默认组合、Smart 药水；
  每根固定 DOP8 或 DOP16，A/B 相同；NoGC 设置均为十进制 16 GB。
- 每臂独立进程、同主机串行执行，各根交替 AB/BA；外部进程上限 360 秒。
  配置的节点数不是所有组合成员相加后的总展开上限。
- Linux 主矩阵使用 Ryzen 7 7840H（8 核/16 线程、约 64 GB RAM）；Windows 代表对照使用
  用户的 i7-14700KF（20 核/28 线程、约 32 GB RAM）。平台分别统计。
- 比较完整请求耗时、计算期进程 RSS 峰值和每 100 ms 采样的 `GC.GetTotalMemory(false)` 峰值。
  后者包含未回收垃圾，不是严格可达对象大小；没有额外强制 GC 制造峰值收益。
  耗时窗口从根捕获到完整 Coordinator 求解结束，不含离线宿主启动、生成场景和最终 JSON 写盘；
  内存采样窗口稍长，覆盖搜索后的指标整理。100 ms 是目标采样间隔，并非实时调度保证。
- 同时保留完整路线哈希、药水序列/数量、质量各分量、展开/转移和组合成员签名。
  内部时间边界由新观察器记录，不能只看最终路线是否胜利。
- 报告全部有效对照，并另列工作量相同且无时间边界的可比子集；不把少算或多用药计为优化。
  单根每臂一次的小幅差异不代表统计显著性，可见 Steam 帧时间未测。

请求、生成场景和哈希固定于
[portable matrix](../../coverage/generated-combat-scenarios/performance-matrix-20260923/manifest.json)。
复跑入口为 [run-matrix.py](../../tools/OfflineSearchHarness/run-matrix.py)，用法见
[宿主文档](../OFFLINE_SEARCH_HARNESS.md#可复跑的-ab-矩阵)。

## 最新上游上的完整结果

34 次 Linux、6 次 Windows 搜索全部 Passed/M2，40 次运行均符合配置；不是 40 个独立场景。
各根等权统计 `exp(mean(log(B/A))) - 1`，负值表示更少／更快。全部 20 对的完整路线哈希、
最终质量字段、药水数量和 ID 序列均相同；没有用额外喝药计为收益。

严格可比子集不是完整语料的替代品。Linux 另有两对触及 300 秒软预算（Regent 精英与普通遭遇），
最终输出相同但实际工作量不同。另一些根的展开数相同，成员跳过理由却从内存不足变为时间份额用尽；
还有部分根因回收内存后能够执行更多成员而增加了工作量。每对的工作与成员签名全部保留。
矩阵工具返回 2 表示存在不满足严格比较条件的对照；本批没有运行失败。

总和之比是另一种权重：Linux 总耗时 +10.88%、RSS 峰值总和 −63.80%；Windows 总耗时 +4.05%、
RSS 峰值总和 −81.10%。累计分配总量之比分别为 −5.08%、+3.98%，并非同工作量分配对照，
不能由这些数值推断模拟器单位工作分配下降。计算期峰值下降也不等于游戏帧率改善。

### 不能忽略的代价与反例

- **dev00 千足虫精英：** 耗时 174.77→254.32 秒（+45.52%），RSS −38.66%；展开 727,176、
  转移 4,056,648 和选择分支 803,401 相同。新增 295 次层间检查点累计 74.77 秒，
  所有检查点总墙钟 22.35→82.83 秒，净增 60.48 秒，解释了请求额外 79.56 秒的大部分。
  GC 暂停总量反而 5.33→3.65 秒；不能只看暂停指标评价回收成本。检查点内部的收集、协调、
  NoGC 重建成本尚未分开测量，约 253 ms 的单次均值不是固定等待；250 ms 延迟仅在另一条战后路径。
- **dev11 Silent 普通遭遇：** 11.26→22.37 秒（+98.68%），RSS −89.07%。基线运行两个组合成员，
  候选运行全部六个；展开 52,796→153,996，转移 224,290→644,172。更多搜索没有改善这次的最终路线。
- **dev10 Ironclad 普通遭遇：** 耗时 +11.13%，RSS **27.88→33.59 GB（+20.49%）**、托管峰值 +23.37%，
  路线相同。两臂都只运行一个组合成员，累计分配接近，展开／转移有小幅差异；未定位峰值回退的独立根因，
  不把它归因于多跑成员，也不以其他场景均值掩盖这个反例。
- Windows Regent 首领同工作量请求 36.16→46.67 秒（+29.06%）；Linux 的同根小幅变化不能覆盖用户机器上的代价。

因此本轮不把 PR 转为 ready，也不宣称满足额外 20% 速度／决策目标。内存收益有多场景证据，
但原先依据 High/6000 节点得出的低耗时代价不能外推到默认 VeryHigh。继续优化应先研究检查点频率／区域重建成本，
以及内存释放与既有组合准入政策的相互作用；本轮未用新阈值、遭遇特例或更大预算掩盖这些问题。

## 游戏本体是否是瓶颈

已定向反编译模型克隆、动态变量与牌堆查询，并核对现有 CPU 样本。
模型克隆调用链占三个样本 SearchStack CPU 的约 3.5%～5.6%，包含下游游戏与 .NET 工作；
没有足够证据把游戏 DLL 整体认定为主要瓶颈。现有牌堆快路径已经 patch 原版 getter，
只在模拟隔离域启用。空动态变量克隆另有旧原型，但缺少完整 A/B，且 patch 会影响克隆并发审核。
本轮没有将它作为收益或新增生产补丁，详见[游戏 DLL 审查](native-helper-audit-20260923.md)。
