## 结论和口径

19 根两侧均获胜，战损、最终 HP、药水、结束回合、胜负和边界指标一致，未发现胜负翻转或本次测量内的质量下降。18 根完整路线 JSON 逐字段相同，1 根不同；不能称为全路线等价。新增四项原生测试全部 Passed，其中三项包含严格增量和完整部署，计划外重算为 0。

**发现并保留一个性能退化反例：**超出回放上限的循环中，4096 个额外动作未交付胜利。ABBA 的求解时间增加 11.3%，Search 累计分配增加 14.9%；采样活对象峰值下降 18.6%。这是时间／累计分配变差而峰值占用降低的明确取舍，修正上一轮“未见明显退化”的泛化表述。当前实现不能被宣称对所有循环都满足无明显性能退化；本轮没有未经验证地修改预算或放宽回放准入。

离线宿主仅作观察，固定 Low、DOP1、默认 GC、20 秒预算、独立串行进程。默认 12000 节点，弃牌选择／取回药水／星能三根为 60000。是否启用零损早停和药水政策逐根写入 suite 并作为 CLI 参数传入。原生 expected 断言由四项游戏测试消费；离线脚本只执行 suite 明确声明的敌人数、终局质量、必要卡牌、选择分支和每 solver 回放上限检查，不冒充支持全部 expected*。每根进程期限 120 秒。

## 补充 DOP 边界

对路线变化根另测 DOP2。开启零损早停时，A 的展开/转移为 DOP1 166/431、DOP2 169/437；B 为 139/359、142/367。两侧各自的完整路线也随 DOP 改变，但质量与 Score 都不变；DOP2 父节点与动作最大实际并发均为 2。因为基线也有此现象，不能算作新回归，也不能说所有循环都具有 DOP 路线／工作量等价。工具正确地将路线差异返回为非零，显式质量和结构检查通过。

## 4096 上限反例：ABBA 与设计含义

7200 HP 的 Letter Opener 根需要 4320 次出牌。这个固定预算下，两侧都因正常回合份额限制选择 T2、战损 4、4321 个含 EndTurn 的动作；不是数学上无零损 T1 路线。完整路线相同，展开仍是 4675，转移却从 9375 增到 13471，多出的恰为未采用的 4096 次回放。

| 指标 | A1 / A2 | B1 / B2 | 均值变化 |
|---|---:|---:|---:|
| 求解 wallSeconds | 4.8917 / 4.8684 | 5.4202 / 5.4404 | +11.3% |
| Search 累计分配，字节 | 516595384 / 516249192 | 593748160 / 593114416 | +14.9% |
| 采样活对象峰值，字节 | 149967192 / 150210736 | 140708648 / 103726640 | -18.6% |
| 工作集峰值，字节 | 385912832 / 386433024 | 373583872 / 368959488 | -3.9% |

首对观察发现代价后，另取完整 ABBA 复核，不把首对重复计入均值。额外探测使用真实模拟并释放临时快照，有限上限保护了终止性，却不保证探测能交付结果。峰值受 GC 与 100 ms 采样影响，不能将其下降理解为没有额外计算和分配。没有可见 Steam 性能结论。

## 审计逐项复核

| 审计项 | 复核和处置 |
|---|---|
| P1：预算／工作量口径 | 风险成立。Expanded 计常规父节点，原本也不是一切模拟的数量上限；额外回放计入 Transitions。4096 属于每 solver，协调器请求可叠加，`SearchRequestWorkTotals` 当前仅汇总，不共享回放额度。主报告明确这两点，所有新结果成对给出展开/转移。请求级共享额度尚未实现。 |
| P2：窄覆盖及失败不重试 | 唯一身份和唯一目标限制成立。原文已写每回合/形状至多一次，但未明确失败也烧掉机会，现已补齐。替代出牌中止、非法、漂移等尚未分开重试；八牌循环手里有其他合法杂牌通常不在加速范围。贸然允许所有失败重试可能放大无收益探测，需与总预算一起设计。 |
| P3：截断计数 | 成立于文案口径。计数仅包含局部时间／节点份额耗尽的 `TURN_LAYER_BUDGET`，不含全局限时、接管等；已收窄说明。 |
| P4：投影低估 | 作为潜在保路风险成立，针对性反例仍缺。静态伤害之后已有 `AdjustMonsterMoveDamage`（TheForgotten、PressureGun、爆炸）与动态 MultiClaw 次数补偿，不能仅凭静态快照判定这些情况漏算。`TryGetForcedMoveId` 当前仅服务蒸汽爆炸的准备／爆炸两阶段，非 EXPLODE 分支跳过的是无攻击准备动作，不是任意强制攻击。尚未构造“实际投影低估且必须保留格挡”的原生反例，不将现有防守测试当成这项通过。 |
| P5：第三方保留上限 | 成立，是原有语义边界。已写入第三方适配手册：仅 SturdyClamp 有显式上限补偿，其他已准入 preventer 按全额保留，适配须覆盖实际结算和估值。 |
| P6：失败后的路线行 | 正索引在失败后会被拒绝，仍需调用者尊重失败边界。但当前测试异常来自 `Capture` 的索引扫描，扫描先于动作胶囊创建，计数 0 不等于本次测试固化了“已有一个动作胶囊却计数 0”。更晚的控件创建异常是否应事务化清理，仍是另一个未验证问题。 |
| P7：显示扫描成本 | 有界周期扫描和字符串比较成本确实存在；相同 presentation 的 Populate 已先复用原控件，通常不重复 Capture。没有可见帧数据支持进一步缓存，本轮不增加缓存状态和失效逻辑。 |

这 19 根是新构造的定向集，不是历史 EQ10/FULL40。当前工作树没有那两套完整计划与根文件，历史报告中的 50 根全等不能移作本轮证据。未完成广泛真实战斗语料验证，也不能从 19 根推出全局质量保证。P4 的低估哨兵、请求级预算及失败重试策略是仍需处理的边界。

## 重跑

基线 DLL 必须具备上一轮共享的固定夹具注入入口；不能直接拿未适配的旧发行 DLL 比较。`--out` 必须不存在，进程串行运行，差异／失败保留并返回非零，不能自动解释为退化。`--abba --cases letter-replay-cap` 用于复核反例。

```bash
python3 tools/OfflineSearchHarness/run_loop_boundaries.py \
  --baseline-dll .local/loop-comparison/baseline/CombatSolver.dll \
  --candidate-dll .godot/mono/temp/bin/Release/CombatSolver.dll \
  --out .local/loop-boundaries-rerun
```

脚本对全部样本的根和完整路线作比较，同时检查显式质量条件；不会自动批准不同路线。原始本地日志位于 `.local/loop-boundaries/`，长期保留的紧凑数据位于本报告链接的 evidence JSON。耗尽反例的 4 HP 战损／T2 期望描述已记录的固定预算行为，不意味着这是无界最优解。
