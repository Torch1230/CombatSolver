# CombatSolver 策略优化方向与架构不足分析

本文面向“**接下来要做策略优化**”这件事，给出三部分结论：

1. **当前架构明显不足的地方**——用可核对的源码与策略优化记录作证据；
2. **之后的方向和建议修改**——按优先级排列，带改动点、验收方式和风险；
3. **落地顺序与反模式**——先做什么、不该继续做什么。

**源码快照：2026-09-27，分支 `main`，已提交 `8915a7c0`。** 本文是静态分析与工程判断，不是行为改动，也没有新增算法验证。带“证据”的小节来自源码或已提交的策略记录；带“判断”的小节是作者推断，需要按 [测试矩阵](../../TEST_MATRIX.md) 逐条验证后才能称为结论。本文与 [求解与搜索策略深度分析](solver-search-strategy-analysis-20260927.md)、[策略优化 Part 1 交接](strategy-optimization-part1-handoff-20260927.md) 配套阅读。

## 0. 结论摘要（先看这五条）

| 优先级 | 问题 | 方向 |
|---|---|---|
| P0 | 搜索不是“一个算法”，而是 Beam + 宽度组合 + 新颖性 + 十几条按包/按卡的特例补充通道，各自有独立预算语义，无法归因、无法保证单调 | 把补充通道泛化为**统一的前沿续搜框架**，并用**单一质量模型**统一比较 |
| P0 | 每修一个世界线报告就新增一条前缀/一次专搜，扩展成本随报告数 O(N) 增长 | 把“开局动作/药水组合/目标/换手”的构造**数据驱动化 + 通用枚举**，特例降为登记项 |
| P0 | 中间保留分与终局排序是两套不可采纳的启发式，中间剪枝会直接决定终局可达集 | 明确**计划/目标层**（能力启动、引擎铺垫、跨回合收益）为一等搜索对象，而不是靠中间分“顺带”保住 |
| P1 | 评估常量手工、按遭遇分叉（Boss/普通不同上限）、没有校准闭环 | 建**离线回归语料 + 校准/灵敏度闭环**，常量可拟合但保持可采纳性与显式失败 |
| P1 | 十余个包在 180 秒上限内没有完整结果，超时根因未系统归因 | 把预算模型、归因和工作量分配统一，把超时包纳入**性能基准** |

一句话：**当前最大的瓶颈不是“Beam 不够宽”，而是缺少一个可解释、可回归、可扩展的搜索与评估框架；继续加特例会在错误的复杂度曲线上越走越远。**

## 2. 当前架构明显不足的地方

下面每条按“现象 → 证据 → 影响 → 风险”展开。P0 是阻塞性问题，P1 是结构性短板，P2 是工程与工具债。

### P0-1 搜索不是单一算法，无法归因、无法保证单调

**现象**：一次请求会依次运行主搜、强制药基线、精确 N 瓶梯度、若干开局补充、能力前缀组合、药水后验、死亡救援、近零战损精炼、中期精炼、回合末选择后验、复制药提前、循环/跨回合通道、可选新颖性与前两回合探索。每一条都有自己的预算扣费与提前停止条件。

**证据**：`CombatSearchCoordinator` 单文件 3,223 行；`RunSupplementalAudits` 与其调用链覆盖十余种诊断模式（如 `EARLY_DISCARD_BEFORE_GENERATION`、`OPENING_TARGET_VARIANT`、`DEFERRED_OPENING_POWER`、`FREE_ATTACK_HAND_SETUP`、`MID_COMBAT_REFINEMENT`、`TURN_END_CHOICE_POSTERIOR`、`EARLIER_COPY_DELAYED_DAMAGE` 等）；`RunOpeningPowerRoutePortfolio` 再叠一层前缀×变体成员。

**影响**：
- 无法回答“这次变好是哪一个机制贡献的”，只能整体 A/B；
- 追加一条补充通道**不保证整条流水线单调**（文档自己也说明“后续能力/药水审计之前，不能据此保证整条流水线单调”）；
- 预算在多个成员间反复分摊，某一机制可能在主搜耗尽时间后根本没有机会运行。

**风险**：继续在每个未追平包上加一条通道，最终会得到一堆互不协调、互相抢预算的路径，且每次改动都可能让别的包退化。

### P0-2 按卡/按包硬编码，扩展成本 O(报告数)

**现象**：大量行为由字符串 ID 与专用分支表达：`NIGHTMARE`、`WHITE_NOISE`、`DUPLICATOR`、`BLOCK_POTION`、`ENTROPIC_BREW`、`TOUCH_OF_INSANITY`、`AMBERGRIS`、`PETRIFIED_TOAD`、`KNOWLEDGE_DEMON 相关`、`TEST_SUBJECT_BOSS/QUEEN_BOSS/AEONGLASS_BOSS` 等，散落在 Search 各分片中。

**证据**：`src/Search` 内 556 处、413 个不同的大写 ID 字面量；能力牌估值已经做了数据驱动注册表，但**开局动作、药水组合、目标选择、换手构造仍主要是逐包新增的私有函数**（`Expansion.Opening` 的 `BuildOpening*` 系列）。

**影响**：
- 每来一个新的“更优世界线”，通常要人工判断该给它加哪种前缀；第 95/89/101 包至今仍未追平；
- 特例之间会互相干扰（例如“药水必须是回合第一动作”的门禁曾排除合法路线，第 58 包才移除）；
- 玩家报告量与代码量近似线性增长。

**风险**：不可能靠堆特例覆盖 100+ 世界线，更不可能覆盖所有卡牌/药水/怪物组合。

### P0-3 中间保留与终局排序脱节，引擎启动缺一等表示

**现象**：中间用 `BeamRankScore`（含持续效果、能量、未来资源等附加项）保留节点；终局用 `FinalPlanOrdering.Select` 的 18 项字典序。两者是独立启发式，中间分高不代表终局能赢。跨回合“先铺垫两三回合再收获”的引擎路线，必须**每一步都在中间排名里活下来**。

**证据**：
- 文档明确“每一步都要活着走出队列，最终能赢的十步组合可能第二步被剪掉”；
- 跨回合收益靠 `SetupValueHorizonTurns = 16`、跨回合探针租约与循环区域预算保护，全是**有界续期**；
- 逐包记录里仍有“默认搜索延后关键能力与用药”“玩家先铺垫能力再收获”的未追平案例（第 100、84、101 包）。

**影响**：能力牌/引擎类路线依赖 `StrategicEffectModel` 的启发式估值是否“恰好”给够分，而不是搜索真的把“启动引擎”当成目标。

**风险**：继续调 `BeamRankScore` 常量是在用调参对抗结构问题；改一个权重要重跑多套基准，且容易顾此失彼。

### P1-4 评估常量手工、按遭遇分叉，没有校准闭环

**现象**：核心权重（HP=30,000、EnemyHp=−10,000、能量 60,000、持续效果 Boss 50,000/普通 150,000、上限 32/4 等）是人工设定；持续效果还有封顶，封顶后无法区分“完整引擎”和“半成品”。

**证据**：`SolverWeights` 全为 `const`；Boss/普通走两套上限；注释直言“旧的总值封顶会让 Echo Form、Curious、Buffer 任意一个生效后立刻饱和”。

**影响**：常量与遭遇强耦合（Boss 战专门放大持续效果），泛化性差；缺少“这些数字是否最优/是否稳定”的证据。

**风险**：手工调参不可复现、不可审计，回归时无法判断是改进还是过拟合。

### P1-5 威胁投影是近似，且有已知偏差

**现象**：`ProjectHpAfterThreat` 只投影当前意图，且只识别 `EXPLODE_MOVE` 一种强制行动，其他强制行动直接跳过；与原生 intent 面板的一致性未证明。

**证据**：源码与调研文档（`docs/archive/research/loop-quality-performance-display-20260921.md`）记录了这两处偏差方向相反。

**影响**：中间排序对“这一轮会不会死”的判断可能与实机不符，直接影响能力启动/卖血的保留决策。

**风险**：投影错判会让搜索系统性高估或低估某些开局，且问题会以“质量偶发变差”的形式表现，难以定位。

### P1-6 药水价值模型静态，联合搜索不足

**现象**：药水机会成本写死 9/14/18，龙涎香写死 40% 最大生命，生成药一律 0；多瓶联合主要靠“精确 N 瓶梯度”逐层搜，生成链与跨回合补槽只在若干特例里覆盖。

**证据**：`PotionUsePolicy` 常量；逐包记录中混沌药水生成链（61/90）仍未追平，玩家自评“混沌药水判断有误”。

**影响**：药水价值与牌组/遭遇/剩余战斗长度无关，容易在“多瓶配合明显划算”时仍保留、或在“明显不值”时误用。

**风险**：继续加特例前缀覆盖个别生成药，问题会在别的药水组合上复现。

### P1-7 集火/目标表示不足

**现象**：集火分组使用自动计算的焦点目标；不保证对“每个玩家可能优先击杀的敌人”都保留独立计划。

**证据**：早期文档已记录“想先拆某个威胁但短期数值不好看的路线，仍可能缺乏独立代表”；逐包记录里 77/97/98 的多目标/转火仍未完全追平。

**影响**：先拆关键小怪、或先铺垫再转火的路线可能没有独立代表而被合并掉。

**风险**：与 P0-3 叠加，目标类路线也依赖“恰好活下来”。

### P1-8 性能与内存架构复杂，超时包未系统归因

**现象**：NoGC 区域、后台回收续搜、内存预约、wave 动态扩缩、并行 lane 归并等占用大量设计与维护成本；同时仍有 13 个包在 180 秒内无完整结果。

**证据**：`SearchGcPolicy`、`SearchWaveMemoryPolicy`、`SmartLayerMemoryForecast` 等；逐包记录的 timeout 包。

**影响**：性能问题与质量问题的边界模糊；超时包既可能是搜索面不足，也可能是工作量浪费，当前没有统一归因入口。

**风险**：把超时当成“再宽一点就行”会掩盖真正的工作量分配问题，也违反仓库“不要用扩大预算掩盖偏差”的约束。

### P2-9 正确性边界导致整请求失败（鲁棒性 vs 静默错误的张力）

**现象**：未知语义按设计显式失败，但失败粒度可能是整次请求（例如第 44 包“两段各自合法、拼起来不可执行”曾令整个请求失败）。

**证据**：第 44、66、68 包的修复过程；交接文档所述的恢复失败边界。

**影响**：正确性优先是对的，但“未支持/非法组合”与“模拟偏差”没有分层处理时，可用性会被少数路径拖垮。

**风险**：若为了鲁棒性引入静默回退，会违反仓库硬约束；因此方向应是**先验证再组合**，而不是吞异常。

### P2-10 串行与并行存在重复实现

**现象**：同一语义在串行展开与并行展开两处有平行实现（如动作准备、选牌回放、药水处理），13 个文件出现 serial/parallel 双路径痕迹。

**证据**：`CombatBeamSolver.Expansion.Choices`、`.ParallelExpansion`、`.AdmittedExpansion`、`.PrimaryChoiceReplay` 等的对称逻辑。

**影响**：行为极易在只改一侧时漂移；测试要覆盖两条路径。

**风险**：这是长期维护成本，也是潜在 bug 温床。

### P2-11 证据链与工具链不完整

**现象**：旧包缺少模型编号映射导致原生状态无法严格比较；检查点因第三方 Mod 或身份映射缺失恢复失败；逐包策略迭代是“40 分钟一包、人工写结论”的手工作业。

**证据**：逐包记录大量“原生状态不可直接比较”“恢复失败”；交接文档描述会话与逐包流程。

**影响**：很多包无法给出可严格比较的结论，优化闭环慢且不可复现。

**风险**：没有自动化回归语料时，任何大改都难以自信地证明“没有退化”。

## 3. 之后的方向与建议修改

以下每条给出：**目标 / 做法 / 主要改动点 / 验收 / 风险**。建议按第 4 节顺序推进。所有建议默认遵守仓库硬约束：正确性优先；不用扩大预算掩盖模拟偏差；未知语义显式失败；Search 不读取设置/UI/runner。

### D1（P0）建立单一“路线质量模型”，统一中间与终局比较

**目标**：消除终局/主要质量比较器族的分叉，让中间排序与终局排序共享同一个可解释的质量向量定义。

**做法**：
- 把“生存 → 战略战损 → 目标达成 → 药水/资源成本 → 回合 → 动作数”定义为一个显式的 `RouteQuality` 值对象（含各项来源与优先级），由现有 `ComparePrimaryQuality` 抽出；
- `FinalPlanOrdering.Select`、`ComparePotionFreePolicyBaselines`、`CompareFinalCandidates`、`CompareCompletedResultPrimaryQuality`、以及 cycle/region/crossturn 的代表比较，改为在**同一份质量向量**上做不同投影（例如 cycle 只取与循环相关的子集）；
- 所有“硬准入门”（强制药、最低用药、龙涎香、保留资源）继续独立于排序，保持显式失败。

**改动点**：新增质量模型类型；替换约 20 个 `Compare*` 的重复字段枚举；补一致性合同测试（同输入在不同入口排序一致）。

**验收**：结构门禁 + 现有终局/保路合同测试 + 一批固定根的前后终局路线逐条一致（无行为变化的重构应先做到逐位一致）。

**风险**：这是大规模重构，必须先做到“纯重构、行为不变”，再谈用它改进策略。

### D2（P0）把补充搜索泛化为“前沿续搜框架”

**目标**：用**一个**通用机制替代十余条按包命名、各带私有预算的补充通道。

**做法**：
- 定义统一接口：从“任意稳定边界节点”或“任意合法前缀”出发，做**有界完整续搜**，最后按 D1 的质量模型整体取优；
- 现有 `fixedPrefixActions` 与 `ReplayAdjustedRoute` 已经是雏形，把它们的入口统一；
- 前缀不再逐包手写，而由**通用前缀生成器**枚举：能力（开局/检索/升级/生成）、药水（每槽首个 + 生成选项）、手牌整理/换手、资源牌、目标变体、延迟伤害提前；
- 每条补搜共享统一的请求时间/节点账本与优先级队列，而不是各自 `min(80_000, …)`、`min(30_000, …)` 硬编码。

**改动点**：新增续搜调度器；把 `RunSupplementalAudits` 内各模式迁移为“前缀来源 + 参数”；删除被替代的专用函数。保留诊断模式名以便对照。

**验收**：对逐包记录中已改好的 31 个包做等价复跑（同根、同预算），确认不退化；对未追平的 89/95/100 等包确认新框架至少能覆盖现有前缀集。

**风险**：迁移期两条路径并存会短暂增加复杂度；必须先冻结行为基线。

### D3（P0）引入显式“计划/目标层”（引擎启动为一等对象）

**目标**：让“先铺垫、后收获”的跨回合计划不再依赖中间分“恰好”活下来。

**做法**：
- 在搜索中显式表示**能力承诺/引擎计划**：记录计划目标（哪张能力、预计兑现回合、已投入资源），像现有的 `PowerCommitment` 租约那样，但把它从“保路席位”提升为“受保护子搜索”；
- 计划由独立的**有界子搜索**从头验证完整收益，而不是只在主 Beam 里靠 `persistentBuffValue` 加分；
- 规划地平线（当前 16 回合无进展 + 探针租约）改为**计划驱动**：有明确计划的路线获得续期，无计划的路线按现有规则收敛。

**改动点**：`PowerCardValuation/Commitments` 扩展为通用计划；`CrossTurnPlanning` 与 `Phases` 接入；终局仍由 D1 质量模型裁决。

**验收**：对 100（实验体早期能力+过牌）、84/101（夜魇复制）等未追平包，在固定短搜预算下证明能找回玩家路线或明确报告边界；对已达标包做不退化哨兵。

**风险**：计划子搜索会与主搜抢预算；必须用共享账本与明确优先级，不能在无证据时扩大总预算。

### D4（P0/P1）数据驱动替换硬编码，ID 集中登记

**目标**：把“按卡/按药写分支”改为**登记项**，降低扩展成本。

**做法**：
- 复用能力牌估值注册表的模式，为**药水**建立登记项：效果分类、机会成本、开局必须/可用时机、生成链规则；
- 为**开局动作**建立登记项：触发条件（模拟事实）、候选生成、保路策略；
- 把散落的 ID 字面量集中到 registry/目录，Search 逻辑只按分类与 Policy 字段分派，不识别具体角色/卡池枚举（沿用 `PowerCardMechanismDispatch` 的做法）；
- 未登记的卡/药保持既有行为或显式边界；登记不得改变状态键与终局政策。

**改动点**：新增 `PotionValuationRegistry`、`OpeningActionRegistry`；迁移现有 ID 常量；更新 `docs/third-party/README.md` 的登记点。

**验收**：迁移后同一批固定根结果逐位一致；新增一个测试用登记项能不写 Search 分支地产生行为。

**风险**：登记点会增加“隐式配置面”，必须同步文档与门禁，避免成为新的漂移源。

### D5（P1）建立评估校准与回归闭环

**目标**：让常量/权重可被证据校准，而不是手工拍。

**做法**：
- 把逐包记录（101 包）与日志站前 150 包整理成**结构化回归语料**（同根、同政策、同预算、记录完整胜负/战损/用药/关键回合）；
- 在[离线搜索宿主](../../OFFLINE_SEARCH_HARNESS.md)上做常量灵敏度与局部校准，输出“改动 → 各根质量变化”矩阵；
- 保持中间评分是启发式、**不是可采纳界**；任何拟合只作用于中间保留，不进入状态键、转置支配与终局政策；
- 用同一语料防止“修好一个包、退化三个包”。

**改动点**：语料 schema 与运行脚本；离线结果入库；灵敏度报告。

**验收**：能对任意权重改动给出“哪些根变好/变差”的表；校准后的默认值在完整语料上不退化。

**风险**：语料质量取决于旧包可比较性；对无法严格比较的包只作方向参考，不作为通过门槛。

### D6（P1）药水价值与联合搜索

**目标**：药水价值随牌组/遭遇/剩余长度变化，多瓶与生成链作为联合对象。

**做法**：
- 机会成本从“固定档位”改为**推导值**：基于该药在本根的实际边际收益（由模拟可得）与稀有度/可再生性，保留 9/14/18 作为先验与下界；
- “生成药链”建模为一条可搜索的**药水序列**，而不是逐个前缀；混沌/蒸馏混沌/熵酿生成的药水按链式来源计价；
- 联合搜索复用 D2 的续搜框架，避免新增专用通道。

**改动点**：`PotionUsePolicy` 扩展为“先验 + 根上下文”；`PotionStrategicCostLookup` 升级；`SimulatedCombatState.Potions` 暴露链来源。

**验收**：61/90 等生成链包在固定预算下追平或给出明确边界；既有无药/省血政策结果不退化。

**风险**：机会成本动态化会让终局排序更难解释；必须保留可审计的确定性口径。

### D7（P1）性能归因与预算模型统一

**目标**：把“超时”拆成可解释的原因，避免用扩预算掩盖。

**做法**：
- 统一请求级账本：时间、节点、转移、选牌、分配、GC、循环回放，按机制维度归因（主搜/各补搜/各组合成员）；
- 对 13 个超时包定位：是节点耗尽、时间耗尽、转置触顶、还是成员互相抢预算；
- 复用并强化离线宿主做 A/B；对并行/内存复杂度只在有实证收益时保留。

**改动点**：诊断 schema 与汇总；必要时调整默认 DOP/预算分配，但**不改变搜索正确性口径**。

**验收**：每个超时包给出单一主因；在不改变结果质量的前提下缩短至少一部分包的墙钟。

**风险**：性能改动容易引入并发/内存偶发问题；按仓库规则只取一次直接证据，不重复验证。

### D8（P1）集火/目标表示

**目标**：为每个“玩家可能优先击杀的目标”保留独立计划代表，而不是只跟自动焦点目标。

**做法**：在目标候选与保路里显式区分集火对象；对“先拆小怪再转火”的路线给独立代表；转火时机由模拟决定。

**改动点**：`Expansion.Candidates` 的目标枚举与 `FocusTargetPressure` 代表通道。

**验收**：77/97/98 等包的多目标路线在固定预算下被找到；单目标包不退化。

**风险**：目标代表增加保路占用，需配额有界，避免挤掉其他通道。

### D9（P2）鲁棒性分层：先验证再组合，不吞异常

**目标**：减少“一个非法组合拖垮整个请求”，同时不引入静默回退。

**做法**：把“不可执行/未支持”的判定提前到组合构造阶段（如第 44 包的修复），失败只淘汰该候选；请求级失败仍可见。禁止宽泛捕获与默认值。

**改动点**：组合前缀的可执行性预检统一入口；失败字典化。

**验收**：构造“两个各自合法但组合冲突”的测试场景，确认不再整请求失败。

**风险**：必须在“显式失败”与“可用”之间保持仓库红线。

### D10（P2）工具链与证据自动化

**目标**：把逐包 40 分钟的人工循环半自动化，降低不可比较结论。

**做法**：
- 模型编号映射：在根捕获时冻结旧/新模型 ID 映射，减少“原生状态不可直接比较”；
- 检查点恢复：把第三方 Mod 缺失/身份映射失败变成明确的前置检查与可复现清单；
- 统一“这条路线在哪层消失”的查询入口（路径诊断已有基础，缺一个聚合查询）；
- 离线宿主支持批量后缀复跑与 ABBA，自动产出可比表格。

**改动点**：Runtime 根捕获与 Testing 工具；离线宿主 CLI。

**验收**：给定一个问题包，一条命令输出“开战根结果 + 每个检查点续搜结果 + 首个差异层”。

**风险**：工具扩张要克制，避免把诊断复杂度带进搜索热路径。

## 5. 明确不建议继续做的事（反模式）

1. **不要靠扩大 Beam/节点/时间/No-GC 来掩盖模拟偏差或估值不足。** 仓库硬约束；且历史证据表明“只翻节点没用、只翻 Beam 也没用”，两者是乘的关系。
2. **不要继续按包新增专用前缀/专用通道。** 这会线性推高复杂度，并让预算分配越来越不可控。
3. **不要在中间评分里塞入“整场必须选择”的信息。** 中间分只是保留启发式，不是可采纳界；把终局目标前移会破坏可解释性。
4. **不要为了鲁棒性引入静默回退/默认值/宽泛捕获。** 正确性优先，未知语义显式失败。
5. **不要把逐包人工结论直接当成永久规则。** 先抽象成可泛化的登记项或框架，再决定是否固化。
6. **不要在验证不足时宣称质量提升。** 同根、同政策、同预算是底线；旧报告差额不是当前收益。

## 6. 风险与开放问题

- **重构风险**：D1/D2 触及终局与保路核心，必须先做纯重构并逐位对照；一旦行为变化混入，后续无法区分“重构 bug”与“策略改进”。
- **预算竞争**：D2/D3/D6 都会引入新的子搜索，若没有统一账本，很容易变成“又一组抢预算的通道”。
- **语料偏差**：101 包是“玩家报告集合”，偏向高战损/罕见遭遇，不能代表整体分布；校准不能只在它上面做。
- **工具边界**：D10 的模型映射与检查点改善受第三方 Mod 与游戏版本影响，可能无法覆盖所有旧包。
- **正确性张力**：D9 的可用性改进必须不越“显式失败”红线；任何“跳过候选”的写法都要被门禁拒绝。

---

## 7. 与仓库约束的对齐检查

- **正确性优先**：所有建议把“模拟/语义正确”置于“搜索质量”之前；D1/D2 作为纯重构先验证行为不变。
- **不掩盖偏差**：D7 明确反对用扩预算掩盖；D5 把常量改进限定在中间保留，不进状态键与终局政策。
- **显式失败**：D9 要求先验证再组合、失败字典化，而非吞异常。
- **单一权威实现**：D1/D4 直接针对“同一比较/同一语义多份实现”的重复。
- **Search 边界**：D3/D4/D6 的登记与计划都保持在 Search 内，不引用 Settings/UI/runner；通过快照注入。
- **证据一次取齐**：第 4 节每阶段只要求一次可比对照与一个不退化哨兵，不重复验证。

## 附：建议的验收清单模板（新增策略机制时）

1. 语义：相关 actual/simulated 严格差分通过；新增分支状态已明确所有权与 Fork/续用。
2. 覆盖：至少一个能复现目标缺口的固定根，证明机制在首个错误边界生效。
3. 不退化：已达标哨兵包（有药/无药/跨回合各一）在同预算下结果不变。
4. 归因：诊断输出能指出机制在哪一层改变了保留/选路。
5. 预算：新机制纳入统一账本，不新增隐式总预算扩张。
6. 文档：更新 `docs/ARCHITECTURE.md`（职责）、必要的 skill、结构门禁；涉及玩家可感知变化时更新发布日志。

本文是方向性分析，不是已批准的改造计划；真正执行前，应按 [战斗语义变更 skill](../../../.agents/skills/combat-semantic-change/SKILL.md)、[搜索性能优化 skill](../../../.agents/skills/search-performance-optimization/SKILL.md) 与[架构边界重构 skill](../../../.agents/skills/architecture-boundary-refactor/SKILL.md) 的流程逐个立项与验证。
