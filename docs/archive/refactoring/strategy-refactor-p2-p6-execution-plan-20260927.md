# 策略与搜索重构 P2–P6 执行计划

状态：P2、P3 已完成并通过固定语料对照；P4–P6 待实施。0.47.1 热修已并入重构分支。

后续指令（2026-09-28）：P6 完成后，如用户没有新的通知，继续执行[原始大重构计划](strategy-refactor-plan-20260927.md)中的 P7、P8。当前 goal 保持进行中，直到这些阶段完成。

## 目标与边界

按 P2→P3→P4→P5→P6 实施。P2–P5 保持行为等价，P6 才增加计划子搜索。一次提交迁移一个可解释边界，不提升版本或发包。Windows 与 Linux 结构门禁规则同步维护；按用户要求只运行 Windows 门禁，不运行 Linux 门禁。

## 实施

1. **P2：请求管线与预算账本。** 建立内部 `SearchPassContext`、`SearchPassResult` 和 `SearchBudgetLedger`。先按原顺序包装主搜、药水审计、补充搜索和无胜利升级；账本接管预算准入与切片，`SearchRequestWorkTotals` 继续统计实际工作量。逐项保留时间与节点算法、阶段名、发布时机和失败行为。
2. **P3：前沿续搜框架。** 用 `ContinuationSearchRequest`、前缀来源和 `FrontierContinuationScheduler` 逐模式迁移固定前缀搜索。保持候选与派发顺序、诊断标签和原去重语义；前缀身份包含完整动作、选择和药水槽。结构调整回放继续独立，工作量计入 P2 账本。移除被取代入口后，协调器主文件以 1,200 行以内为目标。
3. **P4：开局、药水、目标登记。** 建立内部不可变登记项，迁移现有候选生成、药水分类与目标代表规则；未登记对象保持现有处理。只搬迁当前费用与时机规则，不提前实施 P7 的药水价值推导。用测试登记项证明新增规则无需在搜索主流程加分支，同步登记文档与 ID 回流检查。
4. **P5：展开路径统一。** 建立一份 `ExpansionPlan`，串行与并行执行器消费相同动作和选择描述。按选牌、药水、卡牌迁移，保留父节点 Fork 所有权、512 次回放限制、选择预算和原序提交；每类完成后删除对应双实现。
5. **P6：计划层。** 从现有能力承诺扩展 `PlanCommitment`，表达能力启动、复制、药水链及跨回合收益；由登记的机制证据提名计划。`PlanSearchPass` 复用 P2 账本与 P3 调度器进行有界完整续搜，只按真实终局结果采纳；有计划证据的路线可在同一预算内获得续期。新增类型先保持内部接口，不增加公共 API、独立预算池或第二套战斗结算。

## 验收与停损

P2–P5 每阶段结束，复用已保存的 P0 基线各对照一次：#24、#37、#81、#89 和两个生成场景的动作、结果、工作量及剪枝计数须逐位一致。#79、#85 的基线贴近时限，继续列为不可比较。每个迁移边界只做必要的轻量合同检查；P5 另以固定根核对 DOP 1/8 路线及原序提交。不重复生成 P0 基线，不做大批量测试。

P6 依次检查 #100、#101；不足两包时再检查 #84。同根同预算下至少两包优于当前求解器，并记录与可信人工结果的差距；每包累计排查最多 40 分钟。保留已达标根作不可退化对照。期限内不足两包时，明确标记 P6 未完成并记录路线消失的位置，不扩大预算或使用未经验证的改动凑结果。

每阶段更新架构、路线图和测试记录并提交；最终执行 Release 构建、Windows 结构门禁并部署一致的本地 Mod。纯重构出现无法解释的差异，停在该边界修正，不带入下一阶段。
