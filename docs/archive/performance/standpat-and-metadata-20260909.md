## 固定条件与比较口径

使用既有 NECROBINDER / AEONGLASS_BOSS 药水压力输入：38 张跑局牌、19 件额外遗物、两瓶药水及固定开局。只测试 VeryHigh，DOP8，NoGC 配置上限 16 GB，详细诊断与增量回放关闭。搜索预算保持 10,000/50,000 节点、Beam 54/135、动作分支 45/72；每个 unattended 请求总期限 120 秒，首个结果停止。

最终计划在测量前固定为 **B1–C1–C2–B2–B3–C3–C4–B4**。每个条目启动独立进程，用同一冻结构建做一次 Short 预热，再测一次正常配置，随后停止实例。记录所有八个样本，不丢弃慢样本；比较算术均值、范围、首尾漂移、分配、GC 与每 100 ms 采样的进程 RSS 峰值。启动/资源租约等待不进入 solver 耗时，RSS 包含游戏和预热残留。GB 均为十进制。

B4 第一次尝试在进程启动前因主机独占资源排队超时，未产生预热或正式搜索结果；失败启动记录单独保留。该位置等待主机空闲后使用同一冻结构建和原参数补齐，不延长请求期限，也不替换此前七个正式样本。

第一组逐项比较 `RESULT` 中 83 项字段，第二组扩展到 90 项（加入全部七项 deferred-round 诊断），均逐条比较 64 条完整预测 `ACTION`（含目标与选择）。第二组发现其中 `phase / deep_triggered` 实为耗时派生标签，下文保留原比较并说明分类修正；其余 88 项非时序字段全部相同。所有正常请求均为 46,239 展开、636,428 转移、431,140 选择分支，投影战损 9，仍只有死亡路线。字段与所选路线相同是本 fixture 的非退化证据，不等于逐转移严格状态差分或新的胜利证明。

用户此前明确暂不测可见会话，因此本轮口径限定为 headless；不能据此宣称可见 Steam、全部 Mod 组合或所有遭遇均获得相同比例的提速。配置 16 GB 是上限，Runtime 仍按系统余量缩小实际 NoGC 区域，实际区域大小与回收次数单独记录。

## 成本定位与保留实现

基线 Linux perf 使用 `cpu-clock:u`、199 Hz、frame-pointer 调用链和 JIT 符号，得到 28,112 个已解析搜索样本。互斥分组为回放 46.09%、快照 28.35%、Fork 12.30%、其他搜索 9.43%、回放以外的保路 3.82%。其中 coordinator 上的 `EvaluateStandPat` 有 1,381 个样本：旧分类把这部分串行 EndTurn 模拟计入回放，不能只凭“保路 3.82%”推断 coordinator 没有优化空间。inclusive 项相互重叠，不相加，也不把阶段 Stopwatch 时间称为 CPU 时间。

- **EndTurn 探针共用固定 lane。** 原来保路逐项串行执行完整回放；现在只对原规则必经的未缓存探针批量求值。按原 `StateKey` 的首个代表去重，worker 只回传四项标量，临时模拟器在 `finally` 释放，coordinator 原序写缓存和挑选代表。仍使用完整原版回放与快照，没有新节点准入、选择预算或批内回收点。取消/异常先停止派发、排空并记账，再传播原 token/异常；DOP1 保留串行路径。
- **规范药水代价值按单次 solver 复用。** 原保路与终局排序反复遍历整个药水目录；小表按 ID/可再生条件缓存原查询结果。未命中仍走原 `Single`，缺失或重复 ID 继续失败。不存分支药水实例，不把实例可变属性当作规范目录值。
- **复用精确目标类型的缺失证据。** 只有 Ritsu 原全程序集查询成功返回 null 后才能跳过后续解析；校验 AssemblyLoad 代次，并逐次查询弱引用中的动态程序集。新程序集、动态晚建类型、正结果和异常均保留原路径，live 调用旁路。此缓存不是框架安装状态或目标合法性缓存。
- **原生空关键字回调旁路。** 根捕获同时审计基础回调和原生 `Hook.ModifyKeywordsInCombat` 的补丁；确认全部接收者均为默认空操作时，直接查询牌的局部关键字。外部/动态类型、不透明 CardModifier 与补丁仍保留原调用。
- **同根共享不可变监听类型布局。** 2048 个直接映射槽，单布局最多 1024 项；哈希只选槽，完整类型顺序精确匹配后才复用。布局仅含 Type/位图，不含 Model，当前分支继续提供接收者；碰撞和并发替换只导致未命中。最大条目负载约 32 MiB，另有数组/对象开销，随根释放。命中、碰撞与旁路为根累计计数，主搜/恢复数不能相加。
- **原生监听分段与派生前段复用。** 基础前段仅包含阵容、遗物、药水与根 Power；卡牌/球及原生附着效果在后段。成功分段后，卡牌/球变化保留有效/活动前段和 Power 投影；Power、阵容、药水变化仍完整清空。新增 Power 缺少前段锚点时保留原完整列表插入位置；不透明 CardModifier 保留完整列表及追加器上下文。各段不可变，Fork 通过同一上下文重映射，包括完整后段已失效的前段。最新单次正常搜索有效前段复用 576,163 次、构造 622,829 次；该指标为根累计，不能再加主搜索日志。
- **组内排名摘要。** 每个 `RankBest` 组填满后用原 `Max/Min` 冻结最高 Beam 分、最高父分和最低父排名，只在原排名赋值前消费，下一次调用重建。没有复用历史父排名或改变 NaN 规则；比对额外纳入全部七项 deferred-round 指标。
- **同枚举比较去装箱。** 原生 `PowerModel.GetTypeForAmount` 两处 `Equals` 只有在指令形状、枚举底层类型、标签与异常区域均满足条件时才替换为整数比较。虚 getter 与 decimal 分支的调用顺序和次数不变，未知 IL 原样保留；不缓存 Power 类型或层数。
- **局部重复工作。** 同一只读快照的 Power 贡献判定只算一次；引用成员检查按索引遍历，避免接口枚举器装箱；路由父链遇到早于原选择窗口的动作便停止，但保留前一回合的 EndTurn，避免漏掉其携带的下一回合选牌。

新的完整分配采样用于最后三项选择：324,284 个 AllocationTick，估算 34.8599 GB，其中已确认搜索 34.7116 GB，丢失事件/缺失调用栈均为 0。监听布局 `Entry[]` 约 2.1300 GB；Power 贡献查询的两种枚举装箱合计约 0.7733 GB；引用成员检查的装箱枚举器约 0.1317 GB。以上为采样估算，不是精确逐类型字节数。分析器补齐 `AdmittedExpansionJob.Execute` 与 `StandPatJob.Execute` 搜索锚点，避免把作业内分配误归为 lane 基础设施。该 trace 来自布局/贡献判定优化之前，不当作最终版分配分布。

第一组之后的 CPU 采样共 27,038 条，其中搜索调用栈 23,055 条，缺失栈 0、达到 127 帧上限 11；原始 trace 的 JIT 导出失败已修复并重新解析，未重跑搜索。互斥分组为回放 41.05%、快照 30.04%、Fork 14.69%、其他 11.02%、回放外保路 3.21%，仍有未解析 CLR 原生符号。有效监听读取从先前 2,200 条降到 1,167 条；这是不同采样窗的定位证据，不能直接相减为墙钟收益。

最后三个正常单样本为 26.4392/26.5061/26.4646 秒，线程时间线中的 lane CPU 为 108.79/109.87/107.10 秒，lane 调度排队仅约 1 秒。线程组统计包含运行时工作，不把锁等待或 GC 归成纯搜索 CPU。最后一次仍有两次回收，其中一次观测暂停约 2.12 秒；这些数据说明必须用正式交错对照处理回收时点与系统余量的波动。
