# 当前热点与可消除工作（2026-09-12）

## 取证范围

基于 `8faa771` 的 Release 产物，仅使用无头游戏进程。机甲使用 normal VeryHigh，亡灵使用 Low + FixedBudget；DOP8、No-GC 16 GiB、每请求上限120秒，在首个 solver 结果后停止。输入与上一轮对照相同，未调整生产搜索预算或策略。

当前 CPU 数据重新采集，不沿用旧分支比例：同一进程先预热目标场景，再以 `perf cpu-clock:u / 199 Hz / frame pointer + JIT` 采样。机甲 3,850 个可确认搜索样本，亡灵 26,982 个。确认搜索的依据是栈中包含 `CombatBeamSolver`；约82%／81%的全进程样本满足该条件。百分比以已确认搜索样本为分母，不是墙钟时间、FPS或全进程耗时。

## 大头负责什么，能省什么

| 互斥分类 | 机甲 | 亡灵 | 不能直接删除的工作 |
|---|---:|---:|---|
| 快照评估 | 25.61% | 33.55% | 计算状态等价键、威胁、牌序投影和保路特征；省略可能改变合并或排名 |
| 回合模拟 | 34.31% | 17.33% | 执行回合尾、怪物行动和下一回合触发；是路线损失与可行性的依据 |
| Fork | 13.51% | 13.68% | 隔离分支可变对象并重映射引用，避免兄弟分支互相污染 |
| 卡牌执行 | 8.44% | 15.90% | 实际结算卡牌及触发效果 |

**热点内仍能优化。** 判断标准是工作是否重复、默认无操作或可以在明确生命周期内复用，不能把一个大分类的整个占比当作可删除收益。

更细的候选（以下是包含子调用的重叠比例，不能与上表或彼此相加）：

- 卡牌所在牌堆查询约5.43%／5.76%。当前已删除原 getter 的 LINQ 分配，但 `Find` 仍调用列表成员查询。进一步缓存必须覆盖卡牌移动、克隆/临时卡、同一隔离域内变化及第三方牌堆旁路；单凭类型或一次未找到不能证明后续仍未找到。本轮未修改。
- Mirror registry 分发约6.10%／10.82%，其中既有必要处理器调用也有查找；当前已经使用解析快照缓存。不能把整个分发栈当成哈希查找成本，更不能跳过未支持覆盖的风险记录。本轮未修改。
- 卡牌效果归一化约4.86%／3.40%。当前 Power 数量为0，不代表牌上不存在应清除的旧效果；新生成牌还涉及首次进入战斗识别。要跳过全牌扫描，需要跟踪所有相关写入及 Fork 状态，验证面超出一个简单判空。本轮未修改。
- 快照释放成员查询约1.48%／0.19%。原算法按快照引用逐一比较候选与保留节点，形成双重循环；可直接用同样引用语义建立集合，保留相同释放顺序与调用次数。这里是本轮实验对象。该清理发生在 coordinator 的保留结算后；串行部分占总 CPU 的比例较小，也可能对多 worker 搜索的墙钟时间产生更大的影响，具体幅度仍由无采样器 A/B 确认。

状态键也不能只减字段：它决定未来搜索状态是否可合并。Fork 可减少不必要的容器复制，但不能用浅拷贝替代需要隔离的对象。收益来自保留语义的更便宜实现；减少节点、缩短预算、漏掉触发不属于本任务的性能优化。

## 快照释放实验

生产实验只在 `ReleaseDroppedSnapshots` 增加一个局部集合分支：保留数大于8时以 `ReferenceEqualityComparer` 建立 `SimulationSnapshot` 集合；小池继续原扫描。平均成员查询复杂度从 O(候选数×保留数) 降到 O(候选数+保留数)，代价是局部哈希表分配，同时避免为每个候选反复枚举 `IReadOnlyList` 保留池。原接口枚举在实际 List 输入上会产生枚举器装箱；因此总分配并不一定增加，须看实测。8仅是保守的小池分界，本轮没有证明它是全局最优阈值。

独立合同直接提取生产方法，用864组固定种子案例对照原扫描的完整释放调用序列，包含不同节点共享快照、重复引用、保留池独有快照、空输入、阈值两侧及冲突值相等，全部通过。替身合同不等于完整游戏生命周期验证。

实际 A/B 采用 A-B-B-A，每个新进程先预热两个场景，再正式测各一次。基线是本轮剖析版本，候选只含上述14行增量；性能运行不加载采样器。候选第一次启动因隔离产物目录缺少 manifest 而未进入游戏，补齐后继续原序列，该次无样本不计入结果。
