# CPU 微架构、并行利用率与优化复盘（2026-09-08）

[性能目录](../../performance/README.md) · [结构化证据](cpu-microarchitecture-20260908.json)

此前几轮没有取得大收益，不能推出回放、快照或 Fork 已经没有优化空间。主要方法问题是：按大类 CPU 占比选择小部件替换，没有量化小部件实际覆盖多少成本；缓存方案没有先测命中/失效/旁路；把分配减少当作速度线索；只用一次正式样本判断很小的差异。此次先测 CPU 与并行行为，再保留一项由 JIT 汇编直接支持的局部修改。

## 1. 百分比的正确含义

旧 Linux perf 实际 on-CPU 样本中，回放 46.30%、快照 29.68%、Fork 11.33% 是互斥分组。快照组含自己的子调用；Fork 数字只算快照之外的 Fork。3.4% 是当时选中的保路排名子路径，完整 retention 分组为 5.21%，不能互换。

这些百分比按多个线程累计，不是 40 秒墙钟的切片。消除某个 3.4% 的路径，只能直接论证其 CPU 工作量占比；它在关键路径上的位置、能否与其他线程重叠，决定墙钟效果。反过来，提高并行利用率可能同时缩短回放、快照和 Fork 所在的串行等待段，而无需分别重写全部语义。

另修正文档：`SearchPerformanceMetrics.Begin/End` 使用 `Stopwatch.GetTimestamp`，汇总的是经过时间，包含被抢占、锁等待和 GC，不能称为实际线程 CPU 时间。本轮平均用核数另由 Linux `schedstat` 的线程实际运行时间估算。

## 2. 本机并行扩展曲线

本机为 Ryzen 7 7840H，8 个物理核、16 个逻辑 CPU，共享 L3 16 MiB。沿用死灵法师药水投影固定输入和生产 `36aef6a`：极高、NoGC16GB、关闭详细诊断/增量、首结果停止、单请求最多 120 秒。独立 headless 实例先短搜预热，然后按 DOP8 → 1 → 2 → 4 → 8 顺序测量；首尾 DOP8 用于观察漂移，未调整线程亲和性、系统优先级或性能配置。

全部固定短搜都是 10,000 展开 / 144,368 转移 / 101,808 选择，投影战损 3，Passed。聚合工作一致本身不证明所有状态等价。

| 配置 | 搜索秒 | 相对 DOP1 | 搜索相关线程平均用核 |
|---|---:|---:|---:|
| dop1 | 18.0249 | 1.00× | 0.99 |
| dop2 | 11.5682 | 1.56× | 1.66 |
| dop4 | 7.3970 | 2.44× | 2.71 |
| dop8-start | 5.6387 | 3.20× | 4.48 |
| dop8-end | 5.3389 | 3.38× | 4.37 |

平均用核来自每 50 ms 的 `/proc/.../schedstat` 运行时间，按日志观察到的 worker 开始/生命周期结束截取，汇总 expansion lane 和全部 `.NET TP Worker`。它是搜索相关线程的近似值，包含边界采样误差、可能的其他线程池任务，并可能漏掉线程退出前最后一个采样间隔；不是精确的算法 CPU 归因。

首尾相同 DOP8 从 5.6387 到 5.3389 秒，漂移约 5.3%。这直接说明此前单样本中 1–2% 的差异不足以确定真实提速或回退。撤回增加复杂度且未证实收益的原型是工程选择，不能据此断言其优化机制永远无效。

同一进程随后测正常配置并采集 PMU：`e304caaff9954817ae0e07ca6969277d`，40.3314 秒、46,239 展开 / 636,428 转移 / 431,140 选择、Deep，投影战损 9，仍只有死亡路线。搜索相关线程累计约 121.99 CPU 秒，观测窗口约 40.43 秒，平均约 **3.02 核**；运行队列等待合计约 **0.70 线程秒**。记录到的总 GC 暂停 **83.641 ms**、最大 **29.998 ms**；生命周期有 3 次 NoGC restart，不能把另一字段 `noGcRegionRolloverCount=0` 解释为从未重建区域。

这组证据支持先调查程序内部任务粒度、阻塞与准入边界，尚不能确定每个等待原因各占多少。CPU 因访存延迟而停顿时仍被计为运行，因此低平均用核也不能直接归因于内存带宽。内核调度等待与 GC 停顿都不足以单独解释本次空闲空间。

代码线索是现有并行单元主要为父节点：同一预约 wave 内至多 `2×DOP` 个父节点，完成后才能推进下一 wave；单父节点内部的动作/选择通常串行执行。正常配置日志的选择层并行作业数为 0，action replay 作业为 438。43 万选择分支并非全局串行——不同父节点仍并行——但重父任务内部的串行选择链可能形成长尾。**仍需逐父任务服务时间和 barrier 时间，才能量化这一归因。**

## 3. 分支预测与缓存计数

使用 `perf stat`，通过开始/结束日志控制事件启停；事件组运行比例约 32–33%，输出为缩放估计，覆盖整个进程用户态，包括 headless 游戏循环、JIT 与 GC，不是纯搜索。

- IPC 约 **1.873**。
- 分支失误率约 **1.051%**，每千条指令约 **2.41** 次失误。
- 通用 `cache-references` 在本机映射为 `event=0x60,umask=0xff`（所有 L2 请求），`cache-misses` 映射为 `event=0x64,umask=0x09`（L2 指令/数据请求 miss）。两者还包含不同的预取口径，不能当作 LLC miss 率或 DRAM 带宽。事件定义由本机 `perf list --details` 与 Linux AMD PMU 映射核对；参见[内核事件映射](https://raw.githubusercontent.com/torvalds/linux/master/arch/x86/events/amd/core.c)。

另采到 64,823 个 branch-miss 样本，53,097 个栈包含已解析搜索调用。普通 PMI 落点可能有 skid，不能把落点直接当成发生失误的那条分支。尤其 `StateFingerprintBuilder.Add(ulong)` 出现约 2,463 次，但实际 Tier1 汇编没有条件跳转，只有计算与返回；这不是“给 Add 去掉 if”的证据。进一步区分分支与 load 延迟应使用 AMD IBS 的对应事件；[AMD IBS 指标定义](https://docs.amd.com/r/en-US/57368-uProf-user-guide/IBS-Derived-Events)分别描述分支误预测与数据缓存 miss 延迟。

因此，当前证据没有证明大面积去分支、SIMD、绑核或填充缓存行是首选。PGO 与内联也应看实际生成代码；[.NET 编译配置](https://learn.microsoft.com/en-us/dotnet/core/runtime-config/compilation)解释了分层优化与动态 PGO，不能把修改 Mod 项目属性自动视为已经改变游戏宿主的 JIT 配置。

## 4. 四块成本为何没有被前几轮有效削减

| 成本 | 现有证据和此前选点的问题 | 更有针对性的路径 |
|---|---|---|
| 回放 46.3% | 是许多 Hook/状态读取/结算的总和；旧样本的自身热点包括类型检查、字典查找、监听列表构造。已有回调索引没有消除上游监听重建与对象访问，不能按整块 46.3% 估算收益。 | 测父任务长尾与选择链，优先让已准入重任务中的独立动作/选择共享现有 lane；另外量化重复监听重建次数。 |
| 快照 29.7% | 完整状态键约 6.16%，手牌估值约 5.17%，投影洗牌约 3.32%，inclusive 数字不能相加。延迟估值主要改变执行时机，未证明减少调用；牌堆缓存未测命中/旁路，新增字段仍每 Fork 复制。 | 先削掉汇编可见的重复访存；后续按调用数、缓存命中和失效原因决定是否融合计算或缓存。 |
| Fork 11.3% | 旧分组中 Power 克隆、监听缓存恢复及牌堆复制很明显。RNG/小字典实验只减少全搜索约 1% 分配；大部分对象图复制与引用重映射仍存在。少分配不等于少 CPU 周期。 | 测实际克隆/首次写入比例和每类对象的复制量；再评估热点标量连续存储、冷元数据共享和批量复制，先覆盖主要对象图。 |
| 排名子路径 3.4% | 确实消除了重复查表，但只覆盖小项；其串行位置可能重要，不能据此期待整场翻倍。 | 保留已有简单优化，把主要实验预算放在大路径与并行空闲原因。 |

后续调度改动应在**已准入的同一 wave 内**拆独立工作，保持同一 lane 池与 DOP 上限、原父/动作/选择提交顺序及完整内存预约；有限共享选择配额仍按原序结算。直接跨 wave 提前准入可能绕过原本应先发生的 TT/预算更新，不能把这一改变混入“只是调度优化”。这仍是现有引擎调度层的改造，并不要求先换后端。

## 5. 本轮保留的寄存器计算改写

实际游戏 Tier1 汇编显示原 `StateFingerprintBuilder.Add(ulong)` 在每一步反复写回 `_first/_second` 并重新读取。现在两条混合链先在局部 `ulong` 中计算，最后各写回一次，算法、溢出环及 128 位结果不变。两条链互相独立，减少 store/load 依赖；同一输入流的前后状态仍有递推依赖，不能随意按输入元素 SIMD 并行而保持原指纹。

用同一个本地 .NET FullOpts 配置另做代码生成对照，标量函数从 **107 字节到 83 字节**，新函数仅有两次字段读取、两次最终写入。同一探针的字符串重载从 110 字节增加到 171 字节，因此也不能把标量函数变小概括成整体指令缓存占用下降。此独立代码生成探针关闭分层编译，不能把它当作游戏性能样本；游戏的原始 Tier1 汇编另行保存。

`tools/StateFingerprintChecks` 直接编译生产文件，以旧顺序公式作 oracle，200,005 个混合与边界输入后逐步比较两个 64 位结果，Passed。覆盖整数符号扩展、溢出边界、decimal 四字段、bool、Unicode/代理字符、空串与 null。

实际搜索用预先设计的 **A–B–B–A** 序列：每项独立进程，短搜预热后正式一次，不与构建或其他测试并发。A 为原版，B 为寄存器改写：

| 样本 | 秒 |
|---|---:|
| A1 | 5.7484 |
| B1 | 5.5703 |
| B2 | 5.6107 |
| A2 | 5.6504 |

A 均值 5.6994 秒，B 均值 5.5905 秒，相差约 **1.91%**。每版只有两个样本，不声称统计显著或普遍倍率；保留依据还包括汇编中明确消除的访存依赖与很小的实现改动。4 个正式结果的 **90 项非耗时/非并发调度字段和 59 步完整预测动作一致**。这些请求没有部署整场。

Release 零警告/错误；新增指纹 oracle 通过。未测候选正常配置性能、可见 Steam、Windows、整场原生部署或 IBS/DRAM/伪共享归因。本轮没有修改搜索质量、预算、并行度默认值或状态键算法；总体大幅提速仍需处理主要路径与并行利用率。

## 复跑入口

输入与基础命令沿用[上一轮固定短搜命令](bold-backend-experiments-20260908.md#可重跑的基线输入)。并行曲线只依次替换 DOP 为 8/1/2/4/8；正常 PMU 请求移除 `--force-short-search-only`。PMU 命令模板（pid 已属于完成预热的独立实例）：

```bash
perf stat -p "$benchmark_pid" -j \
  -e '{cycles:u,instructions:u,branches:u,branch-misses:u}' \
  -e '{L1-dcache-loads:u,L1-dcache-load-misses:u,dTLB-loads:u,dTLB-load-misses:u}' \
  -e '{cache-references:u,cache-misses:u,L1-icache-loads:u,L1-icache-load-misses:u}'
perf record -k 1 -e branch-misses:u -c 20000 --call-graph fp -p "$benchmark_pid"
```

实际采集用 `perf stat --delay -1 --control fd:...` 接收 `enable/disable`，与日志边界同步；模板中省略控制管道时会包含建局/清理，不能称为相同窗口。.NET 符号使用 `DOTNET_PerfMapEnabled=1`、`DOTNET_EnableWriteXorExecute=0` 与 `perf inject --jit`；原始 perf、线程时间线和脚本留在 `.local/cpu-microarch-20260908/`，不进入源码提交。ABBA 请求曾设置 JitDisasm 过滤变量，但未得到游戏 JIT 文本，因此汇编证据明确分为实际游戏采样生成对象与独立 FullOpts 探针。
