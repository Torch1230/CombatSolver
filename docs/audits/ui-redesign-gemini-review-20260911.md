# Gemini UI 建议复核与当前重构建议

日期：2026-09-11。源码基线：`729b4ad`。范围：用户提供的 Gemini UI 审计全文与当前 UI、Runtime、架构边界。本文是设计审计和实施建议，尚未修改 UI。

## 结论

实施后用户校正：全自动是主要操作，使用绿色按钮并优先展示；执行本回合为次要操作。强制释放内存是常用功能，保留主界面入口。横幅保留醒目及点击隐藏行为，不进行整合。下文中将全自动改 switch、将系统释放下沉设置和整合横幅的建议已撤销，其余内容保留为审计时的分析记录。

建议采纳“按操作目的分组、减少常驻按钮、压缩收起界面、解释不可用状态”的方向。Gemini 的方案不能直接照搬：它混淆了采用路线与执行动作，误判了已有边界保护和快照架构，还把部分设置行为变更夹在视觉重构中。

当前最值得先做的是按钮区。把战斗操作、自动模式、全局开关、维护工具分开，先建立清楚的操作状态，再拆出按钮组件。暂时保留路线渲染和搜索编排，避免一次改动同时改变显示、输入与执行时序。

本次为源码审计，没有打开游戏做视觉观察，没有证明任何具体宽度在实机必然重叠，也没有测量面积或性能改善。Gemini 报告中的视觉结论、用户使用频率和收益百分比不能作为已验证事实。

## 二、原方案中需要纠正的行为与架构建议

### 1. 采用路线不能暗中变成出牌

手动模式下，采用当前路线允许玩家结束本次搜索、保留当前展示的路线，再决定下一步。应用当前回合则有执行意图。原方案合并成一个强主按钮，会丢失前一种操作。

也不能把采用按钮解释为“绝不执行”：当前已开启全自动或已有待部署请求时，采用完成后仍可能沿既有流程执行。重构应保留这些规则，在状态说明里体现，而不是在 UI 内另写一套调度逻辑。

采用必须继续关联屏幕上那条路线的身份。显示快照一致不代表点击时仍有效，命令处理时仍应校验战斗、搜索代次和候选身份，防止按钮切换时采用了另一条路线。

### 2. 全自动关闭与停止计算不是同一个停止

当前 `SetFullAuto(false)` 关闭后续自动推进标志，没有取消正在执行的卡牌或整个部署事务。不能将它命名为“立即暂停”并让玩家期待当前动作立刻中断。

原生选牌也不能统一处理成“关闭全自动，强制人工选择”。部分回合开始选牌有合法的求解器接管路径，另一些情况才需要交还玩家。操作能力必须沿用 Runtime 的判断，尤其要保留此前修复的选牌接管和停止后恢复入口。

### 3. 药水设置的作用范围属于功能规则

当前药水指令会保存并根据槽位和药水身份协调；修改后是否立即重算还取决于暂停和自动计算状态。Gemini 提议“仅本场生效、修改就重算”改变了这两项规则。此次 UI 重构应展示现有作用范围，保留设置语义。

### 4. 结果信息必须遵守实际口径

- 示例中“预计总损 0，本局已扣 4”会混淆总损和后续损失。沿用现有已发生/预计口径；若显示剩余损失，必须明确写“后续预计”。
- 结果是否到达战斗结束、战损是否已知、是否预测胜利、是否经过验证，是不同维度。不能统一替换成“胜局已定”或“高可信度”。
- “无失窃”只能在预测信息支持时使用，信息不足应显示未知。
- 有预算和剪枝的搜索不能宣传为“完整穷尽”。
- 原报告中的卡牌示例名未经官方本地化核对，不进入产品文案。本轮文档也不据此重命名成长策略。

### 5. 视觉收敛不能抹掉信息和快捷入口

单条通知可作为入口，但要显示其他通知数量；阻塞原因和严重错误持续可见，避免更新通知挤掉操作失败原因。第三方兼容性提示继续明确说明已知问题，不增加上传日志引导。

用户此前明确要求主界面快速开关求解器、按钮区的小型自动开启 switch，以及收起时的扣血显示。把这些全部搬进设置不符合现有需求。维护工具可以下沉，常用开关应重新分组。

固定 280×40 的收起示意放不下报告列出的所有文字和按钮；面积减少 45%、零遮挡、性能改善也没有测量依据。设计尺寸应由内容、字体与视口验收确定。

### 6. 新 ViewState 应补齐已有边界

复用现有路线快照，只新增操作能力和必要通知数据。不要在新模型中再次复制战损、药水、路线内容，形成两个结果来源。

原方案的 `ActionCallback` 不属于纯数据，可能通过闭包持有过期对象。使用命令标识和目标身份，由现有 Runtime 入口执行。搜索阶段、部署阶段与自动偏好可以并存，应明确它们的合法关系；一个大枚举再配任意布尔值不能自动消除非法组合。

当前 `SolverOverlay` 是创建 CanvasLayer 的静态类，并非原报告类图所画的 CanvasLayer 子类。引入实例宿主可以分阶段评估；压到 300 行、消灭所有静态字段均不构成正确性或性能验收。路线行已经复用，胶囊存在重建；是否进一步复用应基于分配证据，不先加对象池。

默认 Space/Enter 快捷执行也应后置，先核对原生游戏、选牌页与文本输入的冲突。

## 三、推荐的按钮区设计

### 展开状态：最多三个当前动作，自动模式独立一行

下面是信息结构示意，不是像素定稿；按钮是否出现、是否可用仍由能力状态决定。

```text
求解器 [开关]                   [药水] [成长] [设置] [收起]
必要通知 / 当前阻塞原因                       [其他通知 2]
战损：已发生 … / 预计 …     药水 …     未追回卡牌 / 金币 …
──────────────────────────────────────────────────────
路线与回合内容
──────────────────────────────────────────────────────
[执行本回合]   [重新计算]                      进度 / 状态
本场全自动 [switch]          开战自动开启 [小 switch]
```

搜索中相同区域变为：

```text
[应用当前回合]   [停止计算]   [采用路线]        搜索进度 …
本场全自动 [switch]          开战自动开启 [小 switch]
```

具体取舍：

1. **执行类动作保持最醒目且位置稳定。** 按真实能力显示“执行本回合”或“应用当前回合”；执行中显示进行状态，防止重复提交。
2. **重新计算与停止计算共用一个位置。** 搜索中提供停止，停止处理中显示原因；完成后恢复计算入口。
3. **采用路线是条件出现的次级动作。** 保留手动采用的功能，避免每个状态都放一个灰色按钮。短暂不可用时可保留位置并说明原因，减少布局跳动。
4. **两种自动开关组成模式行。** “本场全自动”与“开战自动开启”分别说明当前行为和后续战斗偏好。后者继续采用用户要求的小 switch；停止本场不偷偷改掉后续偏好。
5. **全局求解器开关放标题栏。** 保持一键可达，避免和“停止这次搜索”挤在一起。
6. **系统释放移到设置的性能页维护分组。** 保留该功能及其管理员授权说明。常态内存信息缩成状态项；达到搜索限制时仍直接提示，不能把内存压力全藏起来。
7. **偷窃策略靠近失窃提示。** 有相关战斗时显示“保牌/保钱”“放走”，避免无关的底栏控件改变主要按钮排列。

这样减少的是同时竞争注意力的动作，而不是删除功能。第一版保留明确文字，避免纯图标让玩家重新猜含义。

### 操作状态验收表

| 场景 | 主动作 | 搜索位置 | 采用入口与说明 |
|---|---|---|---|
| 尚无可执行路线 | 无可执行动作，显示原因 | 开始/重新计算，按能力启用 | 无当前候选时不显示 |
| 搜索中，无可应用当前回合 | 显示等待结果原因 | 停止计算 | 依据独立采用能力，不能只看有没有候选 |
| 搜索中，有可应用当前回合 | 应用当前回合 | 停止计算 | 可采用时显示，解释与出牌的区别 |
| 手动停止后保留候选 | 按当前路线能力判断 | 重新计算 | 保留现有停止后采用路径 |
| 路线就绪 | 执行本回合 | 重新计算 | 按能力显示，避免重复无意义入口 |
| 正在采用或部署 | 进行中状态，禁止重复命令 | 按 Runtime 能力禁用并说明 | 不通过改变按钮文字绕开串行边界 |
| 合法的回合开始选牌接管 | 按原生选牌协调器能力提供入口 | 按实际能力显示 | 不统一归类为“只能手动” |
| 需玩家完成选牌 | 提示当前需完成的选择 | 稳定后恢复计算能力 | 保留手动交互，不由 UI 持有输入锁 |
| 求解器已关闭 | 标题栏开关仍可用 | 明确关闭状态 | 恢复入口始终可发现 |

表中的“可用”以 Runtime 能力为准。UI 不能把“正在搜索”等同于所有动作不可用，也不能把“有路线”等同于所有动作都能执行。

### 收起状态：单独的紧凑视图

```text
战损 …   药水 …   未追回卡牌 / 金币 …              [展开]
当前状态 …              [当前必要动作] [本场全自动状态]
```

收起后不保留整排展开按钮。搜索时必须能停止，待执行时能执行，忙碌时显示阶段；采用、策略和后续偏好可通过展开访问。全局恢复入口应保持可达。

扣血和失窃信息继续复用现有快照；信息长时允许第二行或适当增加宽度。先按内容最小宽度和视口设计，不承诺固定 280 像素。严重阻塞提示不能因收起而消失。

## 四、设置页与路线区域建议

设置页继续使用现有三个分页。最近已修复根容器、页面容器和滚动区的纵向伸展；此次不能继续把旧的底部空白当作尚未处理的固定高度问题。新维护功能先放性能页，不因一个工具再增加第四个分类。

一般设置按“开始计算与自动模式”“执行速度”“显示”组织；性能页按“搜索预算”“停止条件”“资源与维护”组织。帮助文字明确立即生效、下次搜索或后续战斗生效，具体口径以每项真实行为为准。保留可调尺寸和滚动，不强制改为遮挡游戏的全屏弹窗。

路线区域保留卡牌、目标和选牌这类执行关键信息。宽度不足时优先压缩附加统计、次要图标和重复文字，不能把目标/选牌信息一律藏到悬停中。复杂回合允许合理增高；列宽从纯固定下限调整为能随空间收缩的组合，需要以长英文、中文和多次选牌样例验收。

药水与成长策略可以后续改成主面板内子页，减少侧栏覆盖。第一阶段先保留现有边界保护，避免按钮清理同时重做所有页面导航。

## 五、建议的重构顺序

| 阶段 | 改动范围 | 验收重点 |
|---|---|---|
| A：操作状态与按钮区 | 提取只读操作能力、原因和命令目标；拆出按钮组件；重排标题开关、动作行、模式行；维护工具下沉 | 采用/应用/执行语义不变，开关作用域不变，停止与选牌接管不回退 |
| B：摘要、通知与收起 | 复用结果快照，区分主要通知与其他通知；实现紧凑视图 | 总损口径、未知状态、失窃提示正确，收起仍能停止和恢复 |
| C：设置与策略导航 | 整理设置分组与响应式布局，再决定策略子页 | 窄窗、长译文、滚动、焦点恢复；药水持久化和重算规则不变 |
| D：剩余窗口职责 | 按实际耦合拆布局、拖动缩放、生命周期；有证据后再优化胶囊重建 | 场景退出、SL 恢复、语言刷新、订阅释放及快照边界 |

架构边界从 A 开始建立，不能先重写整个 UI，最后才补状态契约。初期保留现有静态入口作为兼容门面，只迁移明确的组件所有权。

具体边界：

- Runtime 提供操作能力和原因，继续独占搜索、采用、部署与原生选择调度。
- UI 只保留展开/收起、活动页面、拖动和尺寸等视图状态。
- 路线转换继续走 `SolverOverlaySnapshot.Capture`；操作刷新不应每帧重新构造整条路线快照。
- 按钮发出明确命令及必要身份，Runtime 再校验当前上下文；不在数据模型中保存执行闭包。
- 设置上传的异步完成继续由设置面板现有邮箱/处理循环接收，不迁移到全局求解调度器。
- 每次职责迁移同步架构地图和对应门禁；避免引入全局事件总线、DI 框架或按行数拆文件。

## 六、实施时的最低验证要求

本节是后续实施验收计划，不是本轮测试成绩。

1. 对应 Release 编译和当前平台结构门禁；跨平台脚本变更时同步两端。
2. UI 结构/事件检查覆盖：搜索无候选、有候选但不能应用、可应用当前回合、手动停止后采用、采用处理中、部署中、关闭后恢复、合法选牌接管、交还玩家选择。
3. 明确断言手动采用不会新增执行意图；已有全自动/排队执行仍遵循原规则；全自动关闭不被宣传或实现为未定义的强制打断。
4. 覆盖展开与收起的扣血、失窃、停止入口；设置拉伸；SL 重建；中英文刷新；场景销毁后的控件与订阅释放。
5. 真实可见布局需要单独视觉验收，headless 无法证明字体、遮挡与点击舒适度。执行时遵循用户不做实机测试的要求；未经视觉验证的部分如实标记。
6. 不为每次纯布局调整跑全套战斗。若确实修改了命令编排，增加最小的采用/部署/原生选牌边界场景。
